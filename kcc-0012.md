## Abstract

This document specifies how a browser wallet exposes a **provider** object to
a web application and how a web application discovers every provider present
in a page. The provider has one `request` method that carries named remote
procedure calls and an event emitter that reports connectivity, network, and
account changes. Discovery uses `window` events so that any number of
wallets can coexist without a shared global variable.

The design mirrors Ethereum's EIP-1193 provider interface and EIP-6963
discovery protocol, and adopts their method-naming, authorization, permission,
and error conventions. It adapts them to Kaspa with network identifiers,
prefixed addresses, sompi amounts, [KIP-5](https://github.com/kaspanet/kips/blob/24db7104f1b52f5c77781f93af6ace0fddf8e80f/kip-0005.md)
message signatures, and a transaction signing method that lets a web
application build a transaction, including inputs authorized by covenants, and
have the wallet sign only the inputs it controls.

## Motivation

Several Kaspa browser wallets inject their own global objects with their own
method names, network identifier spellings, and event names. A web application
that wants to support all of them carries one adapter per wallet, and a new
wallet must persuade every application to add one more. Ethereum went through
the same phase before EIP-1193 gave every wallet the same provider shape and
EIP-6963 replaced the single `window.ethereum` global, whose last-write-wins
semantics made multiple wallets fight over one variable, with an event-based
announcement protocol.

Reusing Ethereum's conventions rather than inventing new ones has two benefits.
Developers arriving from EVM tooling recognize `request`, `accountsChanged`,
error code `4001`, and `wallet_requestPermissions` immediately, and the
tradeoffs behind those conventions were settled over years of production use.

Covenant transactions add one requirement that Ethereum's API does not have. A
web application that builds a transaction whose inputs are authorized by
on-chain rules, such as a token covenant defined by
[KCC-20](kcc-0020.md), needs the wallet to sign only the user's own inputs and
leave every other input untouched. This document specifies that signing mode as an addition.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119 and RFC 8174.

Where TypeScript and prose state the same rule, the prose is authoritative.
TypeScript in this document uses `readonly` and optional markers to convey

### 1. Definitions

The terms below are given in the order of the execution chain they describe:
a web application calls a provider, the provider is exposed by a wallet, and
the wallet talks to a remote.

- **Web application** or **app**: Code running in a browsing context that
  consumes a provider.
- **Provider**: A JavaScript object made available to a web application that
  gives it access to Kaspa through a wallet.
- **Wallet**: An end-user application that manages private keys, performs
  signing operations, and mediates between the provider and a remote. In
  this document a wallet is typically a browser extension, but the interface
  does not depend on that.
- **Remote**: An endpoint, typically a Kaspa node, that services the
  requests a wallet forwards to it.
- **Origin**: The origin of the browsing context in which the provider is
  exposed, as defined by the HTML specification (scheme, host, and port).
- **Account**: A derivation path together with the address it yields. A
  wallet MAY hold several key sets, each with several derivation paths, and
  MAY expose accounts from more than one of them at the same time.
- **Watch-only account**: An account for which the wallet holds the extended
  public key but not the private key. It can supply an address but cannot
  produce a signature for it.
- **Active account**: The account an app treats as the user's current
  choice. It is the first element of the array `kaspa_accounts` returns.
  Every other element of that array is authorized to the same extent, and an
  app MUST NOT require the user to change the wallet's selection in order to
  use one of them.
- **Network identifier**: The string naming a Kaspa network, defined in
  [Section 2](#2-network-identifiers). This document carries it in a field
  named `networkId`.
- **RPC method**: A named procedure invoked through `request`.
- **Restricted method**: An RPC method that requires prior authorization of
  the origin, defined in [Section 5](#5-authorization).

### 2. Network Identifiers

A network identifier is the string form of a Kaspa node's network id. Its
grammar, in ABNF (RFC 5234), is:

```text
network-id   = network-type [ "-" suffix ]
network-type = "mainnet" / "testnet" / "devnet" / "simnet"
suffix       = %x31-39 *DIGIT          ; decimal, no leading zeros
```

A `testnet` identifier MUST carry a suffix, because several test networks
exist and an unsuffixed `testnet` is ambiguous. Producers MUST emit
identifiers in this canonical form. Consumers MUST compare identifiers by
exact string equality and MUST NOT normalize case or separators.

| Identifier   | Network                | Address prefix |
| ------------ | ---------------------- | -------------- |
| `mainnet`    | Kaspa mainnet          | `kaspa`        |
| `testnet-10` | Public test network 10 | `kaspatest`    |
| `devnet`     | Developer network      | `kaspadev`     |
| `simnet`     | Simulation network     | `kaspasim`     |

The table lists the identifiers in use when this document was written. Other
suffixed test networks use the same grammar and the `kaspatest` prefix.
Wallets decide which networks they support.

No CAIP-2 namespace for Kaspa was registered when this document was written.
A proposal to add one to the ChainAgnostic namespaces registry (pull request
193, opened in July 2026 and not yet merged) defines the `kaspa` namespace
with exactly the network identifiers of this section as chain references, so
that `kaspa:testnet-10` names the same network as the provider value
`testnet-10`, and encodes a CAIP-10 account as `kaspa:<reference>:<payload>`,
the address of [Section 7.3](#73-addresses) without its prefix. The proposal
admits only `mainnet` and `testnet-10` as conformant references and excludes
`devnet` and `simnet` because they do not name globally unique networks. If a
namespace is registered, its chain references SHOULD remain the network
identifiers defined here.

Registration is not a precondition for using a network. The grammar above
admits any suffix, so a wallet and an app MAY use `testnet-40` on this
interface whether or not a CAIP reference has been assigned for it, and
nothing in this document depends on the registry. An unregistered network
affects only software that addresses networks in CAIP form, which would have
no identifier to name it by.

### 3. Provider Discovery

Wallets and apps discover each other through two events dispatched on
`window`.

#### 3.1 Events

```typescript
interface KaspaAnnounceProviderEvent extends CustomEvent {
  type: "kaspa:announceProvider";
  detail: KaspaProviderDetail;
}

interface KaspaRequestProviderEvent extends Event {
  type: "kaspa:requestProvider";
}
```

`kaspa:announceProvider` is dispatched by a wallet and carries a
`KaspaProviderDetail`. `kaspa:requestProvider` is dispatched by an app and
carries no payload.

#### 3.2 Provider info

```typescript
interface KaspaProviderInfo {
  readonly uuid: string;
  readonly name: string;
  readonly icon: string;
  readonly rdns: string;
}
```

- `uuid` MUST be a version 4 UUID as defined in RFC 9562, in the canonical
  lowercase hyphenated form. It identifies one provider instance for the
  lifetime of the page and MUST be generated fresh on every page load.
- `name` is a human-readable name of the wallet, intended for display.
- `icon` MUST be a `data:` URI as defined in RFC 2397 that decodes to an
  image. The image SHOULD be square with a minimum resolution of 96 by 96
  pixels. PNG, WebP, and SVG are RECOMMENDED formats.
- `rdns` MUST be a reverse domain name identifier, such as
  `com.example.wallet`, that is a valid domain name under RFC 1034 with its
  labels in reverse order. Reverse domain naming is a naming
  convention. The identifier asserts nothing about
  domain ownership and carries no authenticity (see
  [Security Considerations](#security-considerations)). However, `rdns` MUST be stable
  across page loads and versions of the same wallet, so that an app can
  recognize a wallet it has seen before.

Apps SHOULD NOT use `rdns` or `name` for feature detection; capabilities are
discovered by calling methods, as described in [Section 4.1](#41-request).

A wallet MAY include additional properties in `KaspaProviderInfo`. Apps MUST
ignore properties they do not recognize.

#### 3.3 Provider detail

```typescript
interface KaspaProviderDetail {
  readonly info: KaspaProviderInfo;
  readonly provider: KaspaProvider;
}
```

`provider` is the object defined in [Section 4](#4-provider-interface).

#### 3.4 Wallet requirements

A provider is **ready** when the object described in
[Section 4](#4-provider-interface) exists and is able to accept `request`
calls. A wallet MUST, in this order, once its provider is ready:

1. add an event listener for `kaspa:requestProvider` on `window`
2. dispatch a `kaspa:announceProvider` event.

Announcing on load covers apps that requested before the wallet finished
injecting; answering requests covers apps that initialized after the wallet.

Every `kaspa:announceProvider` event dispatched by one provider instance MUST
carry the same `uuid` and the same `provider` object. The wallet SHOULD freeze
`detail` and `detail.info` with `Object.freeze()` before dispatching, so that
page scripts cannot alter an announcement in flight. Freezing does not
authenticate the announcer (see
[Security Considerations](#security-considerations)).

A wallet MUST NOT remove its `kaspa:requestProvider` listener for the lifetime
of the page.

#### 3.5 App requirements

An app MUST add an event listener for `kaspa:announceProvider` on `window`
before dispatching `kaspa:requestProvider`, and MUST NOT remove that listener
for the lifetime of the page, so that wallets injected later are still
discovered.

An app SHOULD deduplicate announcements by `uuid`, which identifies one
provider instance. An app MAY additionally group providers by `rdns`, which
is stable across page loads, to recognize a previously used wallet.

Two announcements carrying the same `uuid` claim to come from the same
instance. If they differ in `name`, `icon`, `rdns`, or the `provider` object,
the app SHOULD treat the later one as suspicious and SHOULD NOT silently
replace the earlier one. A difference confined to properties this document
does not define is not by itself a reason for suspicion. The same applies to
two announcements that share an `rdns` but carry different `uuid` values.

An app MAY dispatch `kaspa:requestProvider` again at any time to refresh its
list of providers.

#### 3.6 Icons

Because an SVG image can contain script, apps and libraries MUST render icons
only through an `<img>` element or an equivalent mechanism that does not
execute script, and MUST reject an `icon` value that is not a `data:` URI.

#### 3.7 No shared global

This document does not define a global variable such as `window.kaspa`. A
wallet MAY expose a vendor-specific global for its own purposes, but an app
MUST NOT require one, and a wallet MUST NOT rely on one to be discovered.

### 4. Provider Interface

`KaspaRpcSchema` names one entry per method of [Section 6](#6-rpc-methods),
giving that method's parameter tuple and result type, and
`KaspaProviderEvents` names one entry per event of
[Section 4.4](#44-events). Both are written out in
[kcc-0012/interfaces.ts](kcc-0012/interfaces.ts).

```typescript
type KaspaRpcMethod = keyof KaspaRpcSchema;

type RequestArguments<M extends KaspaRpcMethod = KaspaRpcMethod> =
  KaspaRpcSchema[M]["params"] extends readonly []
    ? { readonly method: M; readonly params?: KaspaRpcSchema[M]["params"] }
    : { readonly method: M; readonly params: KaspaRpcSchema[M]["params"] };

interface KaspaProvider {
  request<M extends KaspaRpcMethod>(
    args: RequestArguments<M>,
  ): Promise<KaspaRpcSchema[M]["result"]>;
  on<E extends keyof KaspaProviderEvents>(
    event: E,
    listener: KaspaProviderEvents[E],
  ): this;
  removeListener<E extends keyof KaspaProviderEvents>(
    event: E,
    listener: KaspaProviderEvents[E],
  ): this;
}
```

A wallet that serves vendor methods or emits vendor events widens
`KaspaRpcSchema` and `KaspaProviderEvents` with its own entries rather than
weakening these signatures.

#### 4.1 request

`request` submits one RPC call. The provider MUST identify the RPC method by
`method` and MUST accept the method's parameters as `params`. Every method in
this document takes `params` as an array whose elements are given in the
method's definition; a method that takes no parameters accepts `params` as
`undefined`, whether the member is omitted or present with that value, or as
an empty array.

The returned Promise MUST either resolve with the result defined by the RPC
method or reject with a `ProviderRpcError` as defined in
[Section 4.3](#43-errors). The Promise MUST NOT resolve with a transport
envelope such as a JSON-RPC response object.

The Promise MUST reject when:

- the provider does not support the method, with code `4200`;
- the method is restricted and the origin is not authorized, with code
  `4100`;
- `params` does not match the method's definition, with code `-32602`;
- the user declines a request that needs consent, with code `4001`;
- the method requires the wallet's remote and the provider is disconnected,
  with code `4900`; or
- the provider encounters any other failure, with code `-32603` unless a
  more specific code of [Section 8](#8-error-codes) applies.

These codes are the EIP-1193 and EIP-1474 values, carried over unchanged so
that error-handling code written for an Ethereum wallet keeps working here.
[Section 8](#8-error-codes) lists every assigned code and reserves the rest.

Only the methods marked Required in [Section 6](#6-rpc-methods) are
guaranteed. An app detects any other method, standard or vendor, by calling
it and handling code `4200`. A provider MUST reject a method it does not
support with `4200` before any user interaction and before validating
`params`.

A provider MAY support methods beyond those defined here. Such methods MUST
be named with a vendor prefix that cannot collide with future assignments in
[Section 6](#6-rpc-methods): the reverse domain name of the wallet followed
by an underscore, for example `com.example.wallet_customMethod`. Vendor
methods are subject to the same authorization rules as restricted methods.

#### 4.2 Connectivity

The provider is **connected** when it can service RPC requests for at least
one network, and **disconnected** when it cannot service RPC requests for any
network.

Connectivity is not exposed as a value to read. An app observes it through
the `connect` and `disconnect` events of
[Section 4.4](#44-events), and through code `4900` from a method that needs
the remote. Only the methods listed in [Section 6](#6-rpc-methods) as
requiring the remote are affected; the rest are served by the wallet itself
and MUST work while the provider is disconnected.

#### 4.3 Errors

```typescript
interface ProviderRpcError extends Error {
  message: string;
  code: number;
  data?: ProviderErrorData;
}

interface ProviderErrorData {
  readonly submitted?: readonly TransactionId[];
  readonly pskb?: Pskb;
  readonly [key: string]: unknown;
}
```

- `message` MUST be a human-readable string.
- `code` MUST be an integer from [Section 8](#8-error-codes) whenever a
  listed code applies.
- `data` MAY carry any additional information about the error, such as the
  remote's error message. Two of its members are assigned by this document:
  `submitted`, required by [Section 6.9](#69-kaspa_sendrawpskb), and `pskb`,
  required by [Section 6.10](#610-kaspa_sendpskb). The type stays open so
  that a wallet can add members of its own; a consumer MUST ignore members
  it does not recognize.

#### 4.4 Events

The provider MUST implement `on` and `removeListener` with the semantics of
the Node.js `EventEmitter` API: `on` registers a listener for an event name,
`removeListener` removes a previously registered listener, and both return the
provider.

The provider MUST emit the following events under the stated conditions.

##### connect

When the provider becomes connected, both on first initialization and after a
`disconnect` event, it MUST emit `connect` with:

```typescript
interface ProviderConnectInfo {
  readonly networkId: NetworkId;
}
```

`networkId` is the network identifier of the current network.

##### disconnect

When the provider becomes disconnected, it MUST emit `disconnect` with a
`ProviderRpcError`. The error's `code` MUST be a `CloseEvent` status code as
defined by the WebSocket API (RFC 6455, Section 7.4); `1013` is RECOMMENDED
for a temporary loss of the connection to the remote.

##### networkChanged

When the current network changes, the provider MUST emit `networkChanged`
with the new network identifier.

##### accountsChanged

When the value that `kaspa_accounts` would return changes, the provider MUST
emit `accountsChanged` with the new value, an array of address strings. This
includes authorization being granted or revoked, the active account changing,
the wallet locking or unlocking, and a network change that re-encodes the
addresses with a different prefix.

##### message

The provider MAY emit `message` to deliver notifications not covered by the
events above, with:

```typescript
interface ProviderMessage {
  readonly type: string;
  readonly data: unknown;
}
```

This document assigns no `type` values. Values beginning with `kaspa_` are
reserved for future KCCs. A wallet MAY emit vendor types prefixed with its
reverse domain name and an underscore. Apps MUST ignore types they do not
recognize.

### 5. Authorization

#### 5.1 Origin scope

Authorization is granted to an origin and MUST be tracked per origin. One
origin MUST NOT be able to observe or reuse another origin's authorization.
Whether an app is authorized is the same question as whether the origin
holds the `kaspa_accounts` permission of [Section 6.12](#612-permissions).

Before an origin is authorized:

- `kaspa_accounts` MUST resolve with an empty array and MUST NOT prompt;
- every restricted method MUST reject with code `4100` without user
  interaction; and
- unrestricted methods behave as defined.

#### 5.2 Unrestricted methods

The following methods are unrestricted: `kaspa_requestAccounts`,
`kaspa_accounts`, `kaspa_networkId`, `wallet_switchNetwork`,
`wallet_requestPermissions`, `wallet_getPermissions`, and
`wallet_revokePermissions`. Every other method defined in this document is
restricted.

#### 5.3 Consent

A method whose definition says it prompts the user MUST NOT complete without
explicit user confirmation in an interface the wallet controls and the page
cannot alter. The confirmation MUST identify the requesting origin. If the
user declines, the provider MUST reject with code `4001`.

#### 5.4 Watch-only accounts

A wallet MAY authorize a watch-only account, whose address it can supply but
whose private key it does not hold. When a method would need a signature
from such an account, the provider MUST reject with code `4100` and SHOULD
say in the error's `message` that the account cannot sign. A wallet SHOULD
make the distinction visible when the user authorizes the account, since
nothing in an address reveals it.

#### 5.5 Locked wallets

While the wallet is locked, `kaspa_accounts` MUST resolve with an empty array
and the provider MUST have emitted `accountsChanged` with an empty array when
the wallet locked. `kaspa_requestAccounts` SHOULD prompt the user to unlock.
Restricted methods MAY prompt to unlock or MAY reject with code `4100`.

#### 5.6 Pending requests

While a request that prompts the user is pending for an origin, the provider
MAY reject a further request of the same method from that origin with code
`-32002`.

### 6. RPC Methods

This section is a registry of method names. Names beginning with `kaspa_` and
`wallet_` are reserved for this and future KCCs; unassigned names are reserved
and MUST NOT be given local meaning by an implementation.

| Method                      | Required | Restricted | Prompts | Ethereum analogue           |
| --------------------------- | -------- | ---------- | ------- | --------------------------- |
| `kaspa_requestAccounts`     | Yes      | No         | Yes     | `eth_requestAccounts`       |
| `kaspa_accounts`            | Yes      | No         | No      | `eth_accounts`              |
| `kaspa_networkId`           | Yes      | No         | No      | `eth_chainId`               |
| `kaspa_signMessage`         | No       | Yes        | Yes     | `personal_sign`             |
| `kaspa_sendTransaction`     | No       | Yes        | Yes     | `eth_sendTransaction`       |
| `kaspa_signTransaction`     | No       | Yes        | Yes     | `eth_signTransaction`       |
| `kaspa_sendRawTransaction`  | No       | Yes        | No      | `eth_sendRawTransaction`    |
| `kaspa_signPskb`            | No       | Yes        | Yes     | none                        |
| `kaspa_sendRawPskb`         | No       | Yes        | No      | `eth_sendRawTransaction`    |
| `kaspa_sendPskb`            | No       | Yes        | Yes     | `eth_sendTransaction`       |
| `wallet_switchNetwork`      | No       | No         | Yes     | `wallet_switchEthereumChain`|
| `wallet_requestPermissions` | Yes      | No         | Yes     | `wallet_requestPermissions` |
| `wallet_getPermissions`     | Yes      | No         | No      | `wallet_getPermissions`     |
| `wallet_revokePermissions`  | Yes      | No         | No      | `wallet_revokePermissions`  |

A conforming provider MUST implement every method marked Required and MAY
implement the others. A method marked Prompts requires consent as defined in
[Section 5.3](#53-consent). The Ethereum analogue column is informative.

Four methods require the wallet's remote, because they submit a transaction
to it: `kaspa_sendTransaction`, `kaspa_sendRawTransaction`,
`kaspa_sendRawPskb`, and `kaspa_sendPskb`. Only those MAY reject with code
`4900` while the provider is disconnected. Every other method in this
document is served by the wallet alone, including account enumeration,
network reporting, message signing, and transaction and bundle signing, and
MUST work while the provider is disconnected.

Types named in this section (`Address`, `Hex`, `Uint64`, `Amount`,
`NetworkId`, `TransactionId`, `SerializedTransaction`, `Pskb`) are defined
in [Section 7](#7-encodings).

#### 6.1 kaspa_requestAccounts

```text
params: []
result: Address[]
```

Requests access to the user's accounts. If the origin is not authorized, the
wallet MUST prompt the user to authorize it, and MAY let the user choose which
accounts to expose. If the origin is already authorized and the wallet is unlocked, the
provider MUST resolve without prompting.

On success the result MUST be a non-empty array of the addresses of the
authorized accounts, with the active account first, each encoded for the
current network. After success, `kaspa_accounts` MUST return the same value
until it changes.

The array MAY hold several addresses, drawn from more than one derivation
path and more than one of the wallet's key sets. Which of its accounts a
wallet offers, and which the user authorizes, is the wallet's business; but
every address in the result is authorized for the origin, and an app MAY use
any of them without asking the user to change the wallet's selection. The
first element is the active account only in the sense of
[Section 1](#1-definitions): it is the wallet's current choice, and it is
what an app SHOULD default to when it needs one address.

The result MAY include a watch-only account. An app cannot tell from the
address alone whether the wallet can sign for it.

#### 6.2 kaspa_accounts

```text
params: []
result: Address[]
```

Returns the addresses of the accounts authorized for the origin, with the
active account first, each encoded for the current network, under the rules
of [Section 6.1](#61-kaspa_requestaccounts). Returns an empty array if the
origin is not authorized or the wallet is locked. MUST NOT prompt.

#### 6.3 kaspa_networkId

```text
params: []
result: NetworkId
```

Returns the network identifier of the current network. MUST NOT prompt.

#### 6.4 kaspa_signMessage

```text
params: [message: string, address: Address]
result: Hex
```

Signs `message` with the private key of `address` according to KIP-5:
the UTF-8 encoding of `message` is hashed with BLAKE2b-256 keyed with
`PersonalMessageSigningHash`, and the digest is signed with a BIP-340 Schnorr
signature. The result is the 64-byte signature as 128 hexadecimal characters.

`address` MUST be one of the accounts authorized for the origin; otherwise the
provider MUST reject with code `4100`. `address` MUST be a version 0 or
version 1 address as defined in [Section 7.3](#73-addresses); otherwise the
provider MUST reject with code `-32602`.

The wallet MUST display the complete `message` and the signing address to the
user before signing. The wallet MAY use auxiliary randomness when signing;
verifiers MUST NOT assume a deterministic signature.

A verifier obtains the public key from the address payload: the 32-byte
payload of a version 0 address is the x-only public key, and the 33-byte
payload of a version 1 address with its first byte removed is the x-only
public key.

#### 6.5 kaspa_sendTransaction

```text
params: [{
  from?: Address,
  outputs: Array<{ address: Address, amount: Amount }>,
  payload?: Hex,
  priorityFee?: Amount
}]
result: TransactionId
```

Asks the wallet to build, sign, and submit a transaction paying `amount`
sompi to each output `address`. The wallet selects inputs from `from`, or
from the active account when `from` is absent, adds a change output as
needed, sets the fee, signs, and submits the transaction to its remote.

- `outputs` MUST be non-empty.
- `from`, when present, MUST be an authorized account; otherwise the
  provider MUST reject with code `4100`.
- Every address MUST carry the prefix of the current network; otherwise the
  provider MUST reject with code `-32602`.
- `payload`, when present, is placed in the transaction's payload field.
- `priorityFee`, when present, is added to the minimum fee the wallet would
  otherwise pay.

The wallet MUST display every output address and amount, the fee, and the
presence of a payload before prompting. If the remote rejects the
transaction, the provider MUST reject with code `-32003` and SHOULD place the
remote's message in `data`.

#### 6.6 kaspa_signTransaction

```text
params: [{
  transaction: SerializedTransaction,
  signInputs: Array<{
    index: number,
    sighashType?: number,
    signatureType?: "schnorr" | "ecdsa",
    redeemScript?: Hex
  }>
}]
result: SerializedTransaction
```

Signs the listed inputs of a transaction built by the app and returns the
transaction with those inputs' signature scripts filled in. The wallet MUST
NOT submit the transaction.

- `signInputs` MUST be non-empty and every `index` MUST be a valid input
  index; otherwise the provider MUST reject with code `-32602`.
- The wallet MUST sign only the inputs listed in `signInputs` and MUST leave
  every other input's `signatureScript` byte-for-byte unchanged. An input
  authorized by a covenant carries its authorization in its signature script;
  overwriting it invalidates the transaction.
- For each listed input, the referenced `utxo.scriptPublicKey` MUST be
  spendable by an authorized account, as defined in
  [Section 7.7](#77-signature-scripts); otherwise the provider MUST reject
  with code `4100`. If the wallet cannot construct a signature script for the
  script type, it MUST reject with code `-32000`.
- `sighashType` defaults to `1`. The wallet MUST use the requested type and
  MUST reject with code `-32602` a type it does not implement rather than
  substitute another.
- `signatureType` defaults to the type implied by the script public key
  ([Section 7.7](#77-signature-scripts)). The wallet MUST reject with code
  `-32602` a combination it does not implement.
- The signature hash MUST be computed over the transaction exactly as
  received, including `payload`, `lockTime`, `subnetworkId`, `gas`, and every
  output's covenant binding. The returned transaction MUST be identical to the
  received one except for the `signatureScript` of the listed inputs and the
  `id` field, which MUST equal the identifier of the returned transaction.
- The wallet MUST display every output address and amount, the fee (the sum
  of the listed and unlisted input amounts minus the sum of output amounts),
  and the presence of a payload before prompting.

#### 6.7 kaspa_sendRawTransaction

```text
params: [transaction: SerializedTransaction]
result: TransactionId
```

Submits a fully signed transaction to the wallet's remote and returns its
identifier. The wallet MUST NOT modify the transaction and SHOULD NOT prompt.
If the remote rejects the transaction, the provider MUST reject with code
`-32003` and SHOULD place the remote's message in `data`.

#### 6.8 kaspa_signPskb

```text
params: [pskb: Pskb]
result: Pskb
```

Signs a bundle of partially signed Kaspa transactions
([Section 7.8](#78-partially-signed-transaction-bundles)) in the Signer
role. For every input of every transaction in the bundle whose `utxoEntry`
is spendable by an authorized account, as defined in
[Section 7.7](#77-signature-scripts), the wallet computes the signature
hash of the transaction the PSKT object describes, using that input's own
`sighashType`, and adds one entry to that input's `partialSigs`: where the
signing account's public key in compressed form mapped to the signature.
The wallet MAY add the matching `bip32Derivations` entry for a key it owns.

- The wallet MUST NOT add, remove, or reorder transactions, inputs, or
  outputs, MUST NOT modify any other member, MUST NOT set `finalScriptSig`,
  and MUST NOT submit anything. Finalization and extraction are the app's
  work. Inputs the wallet cannot spend are left untouched.
- The wallet MUST reject with code `-32602` a bundle in which any input of
  any transaction lacks a `utxoEntry`: the signature hash commits to the
  spent outputs, and the reference implementation aborts on such a
  transaction.
- The wallet MUST use each input's own `sighashType`, and MUST reject with
  code `-32602` rather than substitute another type when an input it would
  sign carries a type it does not implement.
- If no input in the bundle is spendable by an authorized account, the
  provider MUST reject with code `4100`.
- The wallet MUST display every output amount and address or script of
  every transaction it signs, the fee of each, and the presence of a
  payload, before prompting.

#### 6.9 kaspa_sendRawPskb

```text
params: [pskb: Pskb]
result: TransactionId[]
```

Finalizes, extracts, and submits every transaction of a fully signed bundle
([Section 7.8](#78-partially-signed-transaction-bundles)).

For each PSKT object, in order, the wallet:

1. sets each input's `finalScriptSig` to the concatenation, over that
   input's `partialSigs` entries in ascending byte-lexicographic order of
   key, of a 65-byte data push (`41`) consisting of the signature in its
   64-byte form (the BIP-340 bytes of a `schnorr` entry; the compact r and s
   encoding of an `eCDSA` entry, not its DER bytes) followed by the input's
   `sighashType` byte, followed by a data push of `redeemScript` (when it is
   present)
2. extracts the transaction the PSKT object describes, as defined in
   [Section 6.8](#68-kaspa_signpskb), with those signature scripts, and
   validates every input's script
3. submits it to its remote with orphan transactions disallowed and records
   the identifier the remote returns; the result lists the identifiers in
   bundle order.

- The wallet MUST reject with code `-32602` a PSKT object with no outputs.
- If finalization or validation fails, the wallet MUST reject with code
  `-32000`. If the remote rejects a transaction, the wallet MUST reject with
  code `-32003`.
- The wallet MUST stop at the first failure and MUST place the identifiers
  of the transactions it already submitted in the error's `data` member as
  `submitted`, an array of `TransactionId`, so that the app can tell how far
  a dependent chain progressed.
- Before finalizing, the wallet MUST check `global.txVersion` and MUST
  reject with code `-32000` a version its implementation cannot extract.
  The reference implementation cannot extract `txVersion` 1 or greater, and
  aborts rather than errors when asked to.
- Before finalizing, the wallet MUST reject with code `-32000` a PSKT object
  with an input whose `utxoEntry.scriptPublicKey` is not one of the types
  of [Section 7.4](#74-script-public-keys). Extraction itself accepts any
  satisfiable script; the reference wallet aborts on a non-standard one.
- The wallet SHOULD NOT prompt: a fully signed bundle carries no authority
  the user has not already granted. It MAY display a summary.

#### 6.10 kaspa_sendPskb

```text
params: [pskb: Pskb]
result: TransactionId[]
```

Behaves as [`kaspa_signPskb`](#68-kaspa_signpskb) followed by
[`kaspa_sendRawPskb`](#69-kaspa_sendrawpskb) applied to its result, under a
single user confirmation that meets the display requirements of
Section 6.8. Every rule and error of both methods applies. If signing
succeeds but submission fails, the error's `data` member MUST also carry, as
`pskb`, the signed bundle with the PSKT objects already submitted removed
and the rest in their original order, so that the app can resume the chain
with `kaspa_sendRawPskb` without a second signing prompt.

#### 6.11 wallet_switchNetwork

```text
params: [{ networkId: NetworkId }]
result: null
```

Asks the wallet to make `networkId` the current network. If it already is, the
provider MUST resolve with `null` without prompting. If the wallet does not
support the network, the provider MUST reject with code `4902`. On success
the provider MUST emit `networkChanged`, and `accountsChanged` if the address
encoding changed, before resolving. The wallet SHOULD cancel requests pending
for the previous network.

#### 6.12 Permissions

```typescript
interface CaveatTypes {
  restrictReturnedAccounts: Address[];
}

type Caveat = {
  [K in keyof CaveatTypes]: { type: K; value: CaveatTypes[K] };
}[keyof CaveatTypes];

interface Permission {
  invoker: string;
  parentCapability: string;
  caveats: Caveat[];
  date?: number;
}

type PermissionRequest = { [method: string]: object };
```

A `Permission` records that `invoker`, an origin, may call the restricted
capability `parentCapability` subject to `caveats`. `date` is the time the
permission was granted in milliseconds since the Unix epoch.

Caveat types form a registry. This document assigns one type; unassigned
types are reserved.

| Caveat type                | Applies to       | Value                                  |
| -------------------------- | ---------------- | -------------------------------------- |
| `restrictReturnedAccounts` | `kaspa_accounts` | `Address[]`, the authorized accounts   |

This document defines one permission, `kaspa_accounts`. Holding it means the
origin is authorized in the sense of [Section 5](#5-authorization).

##### wallet_requestPermissions

```text
params: [PermissionRequest]
result: Permission[]
```

Requests the permissions named by the keys of the request object. A request
for `kaspa_accounts` MUST behave as `kaspa_requestAccounts`. The result MUST
list every permission the origin holds after the request. A request naming a
permission the wallet does not recognize MUST be rejected with code `-32602`.

##### wallet_getPermissions

```text
params: []
result: Permission[]
```

Returns every permission the origin holds. Returns an empty array for an
unauthorized origin. MUST NOT prompt.

##### wallet_revokePermissions

```text
params: [PermissionRequest]
result: null
```

Revokes the permissions named by the keys of the request object without
prompting. After `kaspa_accounts` is revoked, the origin is no longer
authorized, `kaspa_accounts` MUST return an empty array, and the provider
MUST emit `accountsChanged` with an empty array. Revoking a permission the
origin does not hold is not an error.

### 7. Encodings

#### 7.1 Hexadecimal

`Hex` is a string of an even number of hexadecimal characters with no prefix.
Producers MUST emit lowercase. Consumers SHOULD accept either case.
`TransactionId` is a `Hex` of exactly 64 characters.

#### 7.2 Unsigned decimal strings and amounts

`Uint64` is an unsigned 64-bit integer as a decimal string: one or more
digits, no sign, no separators, no exponent, no leading zeros other than the
single digit `0`, and a value no greater than 18446744073709551615. Every
64-bit quantity on this interface uses this form. JSON numbers MUST NOT be
used for them: an IEEE 754 double cannot represent every 64-bit value.

`Amount` is a `Uint64` counting sompi, where one KAS is 100000000 sompi.

#### 7.3 Addresses

`Address` is a Kaspa address string in its standard form, a prefix from
[Section 2](#2-network-identifiers), a colon, and the encoded payload. Three
address versions exist:

| Version | Payload                              | Script type |
| ------- | ------------------------------------ | ----------- |
| 0       | 32-byte x-only Schnorr public key    | P2PK        |
| 1       | 33-byte compressed ECDSA public key  | P2PK ECDSA  |
| 8       | 32-byte BLAKE2b-256 of a redeem script | P2SH      |

Providers MUST return addresses with the prefix of the current network. Apps
MUST NOT strip the prefix.

#### 7.4 Script public keys

In JSON, a script public key is a `Hex` whose first four characters are the
16-bit script version in big-endian byte order and whose remainder is the
script. The current script version is 0, so every script public key in this
document begins with `0000`. The scripts for the three address versions are:

| Address version | Script                                      |
| --------------- | ------------------------------------------- |
| 0               | `20` `<32-byte key>` `ac`                   |
| 1               | `21` `<33-byte key>` `ab`                   |
| 8               | `aa` `20` `<32-byte hash>` `87`             |

Here `20` and `21` are data pushes of 32 and 33 bytes, `ac` is
`OP_CHECKSIG`, `ab` is `OP_CHECKSIGECDSA`, `aa` is `OP_BLAKE2B`, and `87` is
`OP_EQUAL`.

#### 7.5 Serialized transactions

`SerializedTransaction` is the text of a single JSON object (RFC 8259) with
the members below. It is the "safe" JSON schema of the Kaspa WASM SDK, which
produces it with `Transaction.serializeToSafeJSON()` and consumes it with
`Transaction.deserializeFromSafeJSON()`; this section is the normative
definition. Member names are case-sensitive. A member marked optional MAY be
absent or `null`. `Hex[n]` is a `Hex` of exactly `n` characters.

```text
Transaction object
  id               Hex[64]   required  transaction identifier (see below)
  version          integer   required  0 to 65535
  inputs           array     required  Input objects, at least one
  outputs          array     required  Output objects
  subnetworkId     Hex[40]   required
  lockTime         Uint64    required
  gas              Uint64    required
  storageMass      Uint64    optional  also accepted under the name "mass"
  payload          Hex       required  empty string when there is no payload

Input object
  transactionId    Hex[64]   required  identifier of the transaction spent
  index            integer   required  0 to 4294967295, output index spent
  sequence         Uint64    required
  sigOpCount       integer   required  0 to 255
  computeBudget    integer   optional  0 to 65535, defaults to 0
  signatureScript  Hex       required  empty string when unsigned
  utxo             object    required  UtxoEntry object

UtxoEntry object
  address          Address   optional
  amount           Uint64    required  sompi
  scriptPublicKey  Hex       required  Section 7.4
  blockDaaScore    Uint64    required
  isCoinbase       boolean   required
  covenantId       Hex[64]   optional

Output object
  value            Uint64    required  sompi
  scriptPublicKey  Hex       required  Section 7.4
  covenant         object    optional  CovenantBinding object

CovenantBinding object
  authorizingInput integer   required  0 to 65535, index of the input
  covenantId       Hex[64]   required
```

A consumer MUST reject a text that is not a JSON object, that lacks a
required member, or whose member has a type or form other than the one
listed, and MUST ignore members not listed here. A producer SHOULD NOT emit
members not listed here. `storageMass` is ignored for signing.

Every input MUST carry a `utxo` entry, because the signature hash commits to
the spent output's amount and script public key. Consumers MUST NOT trust the
`id` member and MUST compute the transaction identifier from the transaction
contents; a producer that cannot compute it MAY set it to 64 zero characters.

#### 7.6 Signature hash types

`sighashType` is one of the following values. Any other value is invalid.

| Value | Name                     |
| ----- | ------------------------ |
| `1`   | `SIGHASH_ALL`            |
| `2`   | `SIGHASH_NONE`           |
| `4`   | `SIGHASH_SINGLE`         |
| `129` | `SIGHASH_ALL` with `ANYONECANPAY`    |
| `130` | `SIGHASH_NONE` with `ANYONECANPAY`   |
| `132` | `SIGHASH_SINGLE` with `ANYONECANPAY` |

#### 7.7 Signature scripts

An input is **spendable by an account** when its `utxo.scriptPublicKey` is
the version 0 or version 1 script of that account's public key, or, when a
`redeemScript` is supplied for the input, the version 8 script whose hash is
the BLAKE2b-256 of `redeemScript` and the redeem script is one the wallet can
satisfy with a single signature of that account.

Let `sig` be the 64-byte signature and `t` the one-byte sighash type. The
wallet MUST construct signature scripts as follows, using minimal data push
encoding (`OP_DATA_1` through `OP_DATA_75` for pushes of up to 75 bytes, and
`OP_PUSHDATA1`, `OP_PUSHDATA2`, or `OP_PUSHDATA4` for longer pushes):

| Script public key | Default signature type | Signature script                                |
| ----------------- | ---------------------- | ----------------------------------------------- |
| Version 0 P2PK    | `schnorr`              | `41` `sig` `t`                                  |
| Version 1 P2PK    | `ecdsa`                | `41` `sig` `t`                                  |
| Version 8 P2SH    | `schnorr`              | `41` `sig` `t` followed by a push of `redeemScript` |

A Schnorr signature is a BIP-340 signature over the Schnorr signature hash. An
ECDSA signature is the 64-byte compact encoding (r followed by s) of an ECDSA
signature over the ECDSA signature hash. Both hashes are defined by the Kaspa
consensus rules for the given sighash type and differ from each other; a
wallet MUST use the hash matching the signature type.

#### 7.8 Partially signed transaction bundles

`Pskb` is the string form of a bundle of partially signed Kaspa
transactions PSKT.

A consumer MUST reject a `Pskb` that does not begin with `PSKB`, whose
remainder is not even-length lowercase-or-uppercase hexadecimal, or whose
decoded bytes are not the JSON document defined here.

The JSON document is an array of **PSKT objects**. The array MAY be empty.
Each PSKT object has exactly these members, which a producer MUST emit in
this order:

```text
PSKT object
  global   object   required  Global object
  inputs   array    required  Input objects
  outputs  array    required  Output objects
```

Amounts inside a bundle are JSON numbers. `amount` and `blockDaaScore` below are `Uint64Number`, an unsigned
integer no greater than 18446744073709551615 expressed as a JSON number.

```text
Global object
  version           integer   required  PSKT version: 0, 1, or 2; other values invalid
  txVersion         integer   required  0 to 65535, version of the transaction being built
  fallbackLockTime  Uint64    optional  omittable or null
  inputsModifiable  boolean   required
  outputsModifiable boolean   required
  inputCount        integer   required  number of inputs
  outputCount       integer   required  number of outputs
  xpubs             object    required  map of extended-public-key string to KeySource; MAY be empty
  id                Hex[64]   optional  omittable or null, transaction identifier
  proprietaries     object    required  map of string to arbitrary JSON; MAY be empty
  payload           Hex       required  hex string or null
```

```text
Input object
  utxoEntry        object    optional  UtxoEntry object; omittable or null
  previousOutpoint object    required  Outpoint object
  sequence         Uint64    optional  omittable or null
  minTime          Uint64    optional  omittable or null
  partialSigs      object    required  map of compressed-public-key hex to Signature; MAY be empty
  sighashType      integer   required  0 to 255; valid values per Section 7.6
  redeemScript     Hex       required  hex string or null
  sigOpCount       integer   optional  0 to 255; omittable or null
  bip32Derivations object    required  map of public-key hex to KeySource or null; MAY be empty
  finalScriptSig   Hex       required  hex string or null
  proprietaries    object    required  map of string to arbitrary JSON; MAY be empty
```

```text
Output object
  amount           Uint64Number  required  sompi, as a JSON number
  scriptPublicKey  Hex           required  Section 7.4
  redeemScript     Hex           required  hex string or null
  bip32Derivations object        required  map, MAY be empty
  covenant         object        optional  CovenantBinding object; omittable or null
  proprietaries    object        required  map, MAY be empty

UtxoEntry object
  amount           Uint64Number  required  sompi, as a JSON number
  scriptPublicKey  Hex           required  Section 7.4
  blockDaaScore    Uint64Number  required  as a JSON number
  isCoinbase       boolean       required
  covenantId       Hex[64]       optional  omittable or null

Outpoint object
  transactionId    Hex[64]       required
  index            integer       required  0 to 4294967295

CovenantBinding object
  authorizingInput integer       required  0 to 65535
  covenantId       Hex[64]       required

KeySource object
  keyFingerprint   Hex[8]        required
  derivationPath   string        required  BIP-32 path with the leading "m", hardened marked "'", e.g. "m/45'/0'/0/0"
```

##### Signature object

A `Signature` is a JSON object with exactly one member. The member name
selects the scheme; the value is the signature as `Hex`.

| Member    | Scheme         | Value                                 | Length                    |
| --------- | -------------- | ------------------------------------- | ------------------------- |
| `schnorr` | BIP-340        | the 64-byte signature                 | exactly 128 characters    |
| `eCDSA`   | ECDSA, DER     | the DER-encoded signature             | variable, at most 144     |

The member names are exact, including the capitalization of `eCDSA`. A
wallet acting under [Section 6.8](#68-kaspa_signpskb) produces `schnorr`
signatures.

##### Key and path strings

| Where                                   | Form                                                        |
| --------------------------------------- | ----------------------------------------------------------- |
| keys of `partialSigs`, `bip32Derivations` | compressed public key, 66 hexadecimal characters          |
| keys of `xpubs`                         | Base58Check extended public key with the `xpub` version bytes, on every network |
| `keyFingerprint`                        | `Hex[8]`, the first four bytes of the master key identifier |
| `derivationPath`                        | BIP-32 path beginning with `m`, hardened steps marked with `'` |

A producer MUST emit public-key map keys in the compressed form. A consumer
MAY additionally accept the uncompressed 130-character form.

### 8. Error Codes

Error codes form a registry. Codes in the range 4000 to 4999 and in the range
-32768 to -32000 are reserved for this and future KCCs; unassigned codes in
those ranges are reserved. A wallet MAY use codes outside those ranges for
vendor-specific errors.

| Code     | Message                        | Meaning                                                        |
| -------- | ------------------------------ | -------------------------------------------------------------- |
| `4001`   | User Rejected Request          | The user rejected the request.                                 |
| `4100`   | Unauthorized                   | The requested method or account has not been authorized.       |
| `4200`   | Unsupported Method             | The provider does not support the requested method.            |
| `4900`   | Disconnected                   | The provider is disconnected from all networks.                |
| `4901`   | Network Disconnected           | Reserved: no method here targets a network other than the current one. |
| `4902`   | Unrecognized Network           | The wallet does not support the requested network.             |
| `-32700` | Parse error                    | The request could not be parsed.                               |
| `-32600` | Invalid request                | The request is not a valid request object.                     |
| `-32601` | Method not found               | Reserved for pass-through from the remote; providers use `4200`. |
| `-32602` | Invalid params                 | The parameters do not match the method definition.             |
| `-32603` | Internal error                 | An internal error occurred.                                    |
| `-32000` | Invalid input                  | The input is well-formed but cannot be processed.              |
| `-32001` | Resource not found             | A referenced resource does not exist.                          |
| `-32002` | Resource unavailable           | A request of the same kind is already pending.                 |
| `-32003` | Transaction rejected           | The remote rejected the transaction.                           |
| `-32004` | Method not supported           | Reserved for pass-through from the remote; providers use `4200`. |
| `-32005` | Limit exceeded                 | The request exceeds a limit set by the wallet.                 |

The `message` column is the RECOMMENDED value of `ProviderRpcError.message`
when no more specific text is available.

## Rationale

**Why copy Ethereum.** EIP-1193 and EIP-6963 are the most widely deployed
wallet interoperability conventions in any ecosystem. Their shapes are known
to every developer who has integrated an EVM wallet, their failure modes are
documented, and library authors can port existing connector code with a
change of method names. Inventing a Kaspa-specific shape would cost adoption
without buying anything the Kaspa model needs, with the exception of
transaction signing, discussed below.

**Why events rather than a global.** A shared global such as
`window.kaspaProvider` is last-write-wins when several wallets are installed,
and its presence at page load depends on injection timing. EIP-6963 solved
both problems with an announce-and-request pair on `window`; this document
adopts it unchanged apart from the event prefix. The KIP-12 draft named the
announcement event `kaspa:provider`; this document uses
`kaspa:announceProvider` to mirror `eip6963:announceProvider` exactly, since
the event pair is the one part of the protocol that every library must
hard-code.

**Why `uuid`, `name`, `icon`, and `rdns` are the only standard fields.** These are the four
EIP-6963 fields, and existing wallet-selection user interfaces know how to
render them. The KIP-12 draft also carried an extension `id` and a `methods`
array. The former duplicated `rdns`; the latter advertised capabilities that
a page script could equally announce, so apps could not trust it. Capability
discovery through code `4200` costs one rejected call and cannot lie.

**Why `kaspa_` and `wallet_` with underscores.** Ethereum separates
chain-scoped methods (`eth_`) from wallet-scoped methods (`wallet_`), and
JSON-RPC method names conventionally use an underscore. The KIP-12 draft used
`kaspa:connect` style names, which read like event names and collide with the
discovery events' namespace.

**Why `networkId` rather than `chainId`.** Ethereum's `chainId` is a
hexadecimal integer identifying a chain. Kaspa's networks are named, not
numbered, and the node's own string form is already used by every Kaspa
tool, so `networkId` describes what the field actually carries. It also
matches the vocabulary the deployed Kaspa wallets already use, which expose
a network getter, a network switch, and a network-changed event. The value
is the canonical identifier of [Section 2](#2-network-identifiers) rather
than a wallet-specific spelling such as `kaspa_testnet_10`.

**Why `kaspa_signTransaction` takes a list of inputs.** In the account model a
wallet signs a whole transaction. In the UTXO model a transaction routinely
mixes inputs owned by the user with inputs owned by other parties or by
covenants whose signature scripts are already in place. The wallet therefore
needs to be told which inputs are its business, and must promise not to touch
the rest.

**Why a separate `kaspa_signPskb`.** Multi-party and multi-signature flows
need more than a finished transaction: partial signatures from several
signers, redeem scripts, and key-derivation metadata, accumulated across
participants who do not trust each other. `kaspa_signPskb` carries those in
the bundle format of
[Section 7.8](#78-partially-signed-transaction-bundles), whereas
`kaspa_signTransaction` writes finished signature scripts and suits the
common single-signer case. An earlier revision omitted the bundle method
because its schema was defined only by the SDK; Section 7.8 now specifies
it, derived from the kaspa-wallet-pskt crate and verified against that
implementation.

**Why two bundle-submission methods.** An app that has co-signed a bundle
needs a way to get it on chain without finalizing and extracting in the
page, which would require the SDK in every app that uses bundles.
`kaspa_sendRawPskb` moves that work to the wallet, which already has it,
and `kaspa_sendPskb` folds signing in for the single-signer case, as the
reference wallet's own broadcast and send operations do and as the KIP-12
draft did. The reference implementation skips a transaction that fails and
continues with the next; this document instead requires stopping at the
first failure and reporting what was submitted, because a bundle is usually
a dependency chain and a silent gap in it is worse than a reported one.

**Why no node pass-through.** Ethereum providers forward `eth_getBalance` and
similar read methods to the node. Apps on Kaspa read UTXOs and balances
from public nodes or indexers by address, which the app already holds, and
standardizing a pass-through surface would tie this document to the node RPC.
A future KCC may define one.

**Why no network-adding method.** EIP-3085 exists because EVM chains are
user-addable by URL. Kaspa networks are enumerated by the node, so
`wallet_switchNetwork` with code `4902` suffices.

**Why sompi strings.** A JavaScript `number` cannot represent every 64-bit
sompi value, and a rounding error in an amount is a fund-safety defect.

**Alternatives considered.** As Ethereum can be considered to be the biggest and
most well adopted standard, no specific alternatives were considered. This
KCC was a continuation and adaptation of KIP-12.

## Backwards Compatibility

No previous standard exists.

## Conformance Vectors

The machine-readable form of these vectors is under
[kcc-0012/vectors/](kcc-0012/vectors/) and is authoritative. Every
construction defined in the Specification is covered: network identifiers,
provider info, hexadecimal and unsigned decimal strings, error codes,
message signatures, script public keys, serialized transactions, signature
scripts, partially signed transaction bundles, and bundle finalization and
submission.

### Network identifiers

Valid: `mainnet`, `testnet-10`, `testnet-11`, `testnet-12`, `devnet`,
`simnet`.

Invalid: `testnet` (missing suffix), `testnet-010` (leading zero),
`testnet-` (empty suffix), `testnet_10`, `kaspa_mainnet`, `kaspa_testnet_10`,
`Mainnet`, `MAINNET`, `mainnet ` (trailing space), ` mainnet` (leading
space), and the empty string.

### Provider info

`uuid` valid: `350670db-19fa-4704-a166-e52e178b59d2`,
`9b2ee4a6-6c3f-4c6a-8f0e-1d2c3b4a5e6f`.

`rdns` valid: `com.example.wallet`, `org.example.wallet-two`,
`io.kaspa.example`.

`icon` valid: any `data:` URI, for example
`data:image/svg+xml,%3Csvg%20xmlns%3D%22http%3A%2F%2Fwww.w3.org%2F2000%2Fsvg%22%2F%3E`
and a `data:image/png;base64,` URI.

### Hexadecimal and unsigned decimal strings

`Hex` canonical: the empty string, `00`, `deadbeef`, `0151`. Accepted but
not canonical: `DEADBEEF`, `DeadBeef`.

`Uint64` valid: `0`, `1`, `100000000`, `18446744073709551615`.

### Provider errors

The codes, names, and recommended messages of [Section 8](#8-error-codes).

### Message signatures

Vectors from KIP-5. Each row gives the message, its BLAKE2b-256 digest keyed
with `PersonalMessageSigningHash`, the x-only public key, and a signature that
MUST verify. The signatures were produced with the listed auxiliary
randomness; a wallet using different randomness produces a different but
equally valid signature.

| Message         | Digest                                                             |

### Partially signed transaction bundles

A canonical `Pskb` ([Section 7.8](#78-partially-signed-transaction-bundles))
is in [kcc-0012/vectors/pskb.json](kcc-0012/vectors/pskb.json), together with

A consumer MUST reject:
- the same string with its `PSKB` prefix removed
- a `PSKB` prefix followed by the hexadecimal of a JSON object rather than an

- a `PSKB` prefix followed by odd-length hexadecimal

`-32602`; and a 2-of-2 multisig input carrying one signature, which

## Security Considerations

**The provider is adversary-controlled.** The provider object lives in the
page and can be read, wrapped, or overwritten by any script there. A wallet
MUST NOT place private data in it, MUST isolate the wallet from the page,
MUST validate every value received from the page, and SHOULD rate-limit
requests. The trust boundary is the wallet's own user interface, not anything
the page shows.

**Announcements prove presence, not identity.** Any page script can dispatch
`kaspa:announceProvider` with another wallet's `name`, `icon`, and `rdns`.
Freezing the detail only prevents an announcement from being altered after
dispatch. A spoofed provider holds no keys and cannot forge a signature; the
realistic risk is display spoofing that sets up a phishing flow. Apps MUST
NOT treat `name`, `icon`, or `rdns` as evidence of anything, and every
consent flow happens in the wallet's own interface.

**Icons.** An SVG icon can contain script; a remote icon leaks the user's
visit to a third party and can change after review. Hence the `data:` URI
requirement and the `<img>` rendering rule.

**Origin isolation.** Permissions are keyed by origin. A wallet SHOULD NOT
expose a provider to cross-origin frames unless it attributes each request
to the frame's own origin. A wallet's transport between page and extension
MUST verify the origin of every message it accepts.

**Account exposure.** Exposing accounts to every page enables tracking across
sites. `kaspa_accounts` therefore returns nothing until the user consents,
and `kaspa_requestAccounts` exists so that consent is explicit.

**Session restore.** An app MAY remember a wallet's `rdns` and, after a
reload, call `kaspa_accounts` to redisplay accounts without prompting. Because
`rdns` is spoofable, an app SHOULD require a fresh explicit selection of the
wallet by the user before routing a signing request to a provider it did not
select in the current page session.

**Blind signing.** The wallet's confirmation for any signing method MUST show
enough for the user to judge the request: for transactions, every output and
amount and the fee. For messages, the complete message. A wallet SHOULD warn
when a message is not printable text.

**Message replay.** KIP-5 keys the message hash with a domain separate from
the transaction signature hash, so a signed message cannot be replayed as a
transaction signature. Replay of a signed message between apps is not
prevented by this document. An app that uses `kaspa_signMessage` for
authentication SHOULD bind the message to its own domain, a nonce, and an
expiry, in the manner of Ethereum's EIP-4361.

**Network changes.** Because address strings and the spendability of UTXOs
depend on the network, a provider MUST keep `kaspa_networkId`, `networkChanged`,
`kaspa_accounts`, and `accountsChanged` consistent at all times. An app
SHOULD discard cached state on `networkChanged`.

**Denial of service.** A page can issue requests in a loop. Wallets SHOULD
coalesce or reject duplicate pending prompts with code `-32002` and MAY
throttle an origin with code `-32005`.

## Abstract

This KCC defines a six-level [BIP32](https://github.com/bitcoin/bips/blob/130b8e0fa7f30fa45532f080b87b8db27a79e46e/bip-0032.mediawiki) derivation hierarchy for Kaspa P2PK and multisig wallets.
Hardened levels separate spending conventions, networks, signature schemes, and accounts. Two non-hardened levels allow account extended public keys to derive receiving and change keys. For multisig wallets, the convention also specifies per-address public-key encoding and sorting, while leaving the script template to the wallet policy.

## Motivation

A wallet should not reuse keys between mainnet and testnet (coin_type), between P2PK and multisig (purpose), or between Schnorr and ECDSA (sig_scheme). Explicit derivation boundaries prevent this reuse and make wallet recovery consistent across implementations.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html). Lowercase forms of these words carry no normative force.

The prose in this section is authoritative for the derivation and sorting rules.

### Path levels

The path has exactly six child levels below the BIP32 master node `m`:

```text
m / purpose' / coin_type' / sig_scheme' / account' / change / address_index
```

The first four levels MUST use hardened derivation as defined in [BIP32](https://github.com/bitcoin/bips/blob/130b8e0fa7f30fa45532f080b87b8db27a79e46e/bip-0032.mediawiki#child-key-derivation-ckd-functions), `change` and `address_index` MUST use non-hardened derivation.

Each path component before applying hardening MUST be an integer from `0` through `2^31 - 1`, inclusive. An apostrophe denotes adding `2^31` to that component's BIP32 child number. Wallets MUST reject paths with the wrong number of levels, incorrect hardening, or out-of-range components.

Master-key generation and child-key derivation MUST follow BIP32, including its invalid-key handling. BIP32 derivation MUST retain the full compressed public key at intermediate nodes, including in Schnorr subtrees. The x-only encoding is applied to the final derived key, not to the BIP32 derivation inputs.

### Value registries

The `purpose`, `coin_type`, and `sig_scheme` tables below define registries over the integer range `0` through `2^31 - 1`. The listed values are their initial assignments, all unassigned values are reserved. New values are assigned only by a Final KCC that claims them, following KCC-0. Implementations MUST reject unassigned values rather than assigning them local meaning.

### Purpose

The purpose selects the spending convention:

| Value | Convention |
| ----- | ---------- |
| `44`  | P2PK       |
| `45`  | Multisig   |

For purpose `44`, the derived key is used in the existing P2PK form for the selected signature scheme. For purpose `45`, the derived keys are used in a multisig policy, with each key verified using its cosigner's selected signature scheme.

Hardened derivation is REQUIRED at this level.

### Coin type

The coin type separates the key space by network:

| Value    | Network       |
| -------- | ------------- |
| `111111` | Kaspa mainnet |
| `111112` | Kaspa testnet |
| `111113` | Kaspa simnet  |
| `111114` | Kaspa devnet  |

Hardened derivation is REQUIRED at this level.

### Signature scheme

The `sig_scheme` level selects the signature scheme for all keys in its subtree:

| Value                  | Signature scheme           |
| ---------------------- | -------------------------- |
| `0`                    | Schnorr over secp256k1     |
| `1`                    | ECDSA over secp256k1       |
| `2` through `2^31 - 1` | Reserved for future scheme |

Both defined schemes use BIP32 key derivation over secp256k1. Their different indices separate the derived keys, the scheme also determines the public-key encoding and signature verification used for each key in the resulting script.

Hardened derivation is REQUIRED at this level.

### Account

Accounts are numbered starting at `0`, independently within each `(purpose, coin_type, sig_scheme)` subtree. Wallets SHOULD allocate them sequentially.

The account node is:

```text
m / purpose' / coin_type' / sig_scheme' / account'
```

Its extended public key can derive both address chains without access to private keys.

For multisig, all cosigners MUST use the same account index and network, but MAY use different signature schemes. Each cosigner derives its account key from its own seed. The threshold, cosigner account keys, their origins and signature schemes, and script construction MUST be retained as wallet policy metadata.

Hardened derivation is REQUIRED at this level.

### Change

The `change` level selects one of two chains:

| Value | Chain                         |
| ----- | ----------------------------- |
| `0`   | External: receiving addresses |
| `1`   | Internal: change addresses    |

Wallets MUST reject other values. Non-hardened derivation is REQUIRED at this level.

### Address index

Addresses are numbered sequentially from `0` within each chain.

Non-hardened derivation is REQUIRED at this level.

### Multisig derivation and key sorting

For each multisig address, the wallet MUST derive the same `change / address_index` suffix from every cosigner's account extended public key.

The wallet MUST encode each derived public key according to its cosigner's signature scheme: ECDSA uses 33-byte compressed public keys, and Schnorr uses 32-byte x-only public keys. The wallet MUST sort these encodings in ascending lexicographic order before inserting them into the multisig redeem script. This extends [BIP67](https://github.com/bitcoin/bips/blob/130b8e0fa7f30fa45532f080b87b8db27a79e46e/bip-0067.mediawiki)'s deterministic key-sorting rule to Schnorr and mixed-scheme key sets. Each key's signature scheme MUST remain associated with that key during sorting and script construction.

Sorting MUST be performed separately for every address, after deriving its public keys. A cosigner's position in the redeem script can change between addresses.

The wallet policy MUST define a deterministic script construction that enforces the threshold and verifies each derived key using its cosigner's selected signature scheme. A single `OpCheckMultiSig` or `OpCheckMultiSigECDSA` applies one signature scheme to all keys and cannot implement a mixed-scheme policy. Mixed-scheme policies require a script construction with scheme-specific signature checks.

This convention specifies key derivation, encoding, and ordering. It does not define redeem-script bytes, script hashes, address encodings, or signature serialization. Identical derived keys produce interoperable multisig addresses only when wallets also agree on the retained policy and script construction.

Wallets MAY support only a subset of the multisig policies permitted by this KCC. An operation requiring an unsupported signature scheme or script construction MUST fail explicitly.

### Account discovery

Recovery MUST treat each supported `(purpose, coin_type, sig_scheme)` combination as an independent search space. Finding no history in one combination MUST NOT terminate discovery in another. Multisig recovery additionally requires the wallet policy metadata described above.

This KCC does not prescribe account or address gap limits. Recovery software SHOULD retain or request the wallet's account-allocation and gap-limit settings rather than assuming that a seed alone identifies every used account and address.

## Rationale

The additional hardened signature-scheme level prevents a wallet from deriving the same private key for Schnorr and ECDSA within one spending convention and network. Separate purpose and coin-type levels similarly isolate P2PK from multisig and distinguish the four Kaspa networks. Hardened accounts limit the effect of exposing an account's private keys.

Using metadata alone to distinguish schemes or networks would leave the private keys shared. A five-level hierarchy such as [BIP44](https://github.com/bitcoin/bips/blob/130b8e0fa7f30fa45532f080b87b8db27a79e46e/bip-0044.mediawiki) does not provide this signature-scheme boundary. [BIP43](https://github.com/bitcoin/bips/blob/130b8e0fa7f30fa45532f080b87b8db27a79e46e/bip-0043.mediawiki) motivates purpose-based separation, while [BIP48](https://github.com/bitcoin/bips/blob/130b8e0fa7f30fa45532f080b87b8db27a79e46e/bip-0048.mediawiki) provides related work on separating multisig script types. This convention uses its own six-level layout and does not claim compatibility with those wallet layouts.

Sorting after derivation allows each address's script key order to be reconstructed without a privileged cosigner or a persistent cosigner ordering. Sorting account keys once would not guarantee that their descendants remain sorted. Encoding each final key before sorting makes ordering independent of wallet-internal point representations. Retaining the scheme alongside each key allows mixed-scheme policies without selecting a script template on behalf of wallets.

## Backwards Compatibility

KCC-3 is an optional wallet derivation convention and requires no consensus changes. Adopting it requires using the hierarchy specified here. Other derivation schemes remain usable on the network.

Adding a hardened level or changing a path component derives different keys and addresses from the same seed. Existing funds remain at their original addresses. Wallets adopting this convention SHOULD retain the original derivation paths and policy metadata for recovery and spending, migration to new addresses requires an explicit transaction. Import and recovery interfaces SHOULD identify the derivation convention instead of silently interpreting a legacy seed or account key as using this hierarchy.

## Examples

These paths illustrate the hierarchy. Each multisig row shows the complete path for one cosigner's key, the signature scheme may differ between cosigners.

| Network | Convention | Scheme  | Account | Chain    | Address index | Path                      |
| ------- | ---------- | ------- | ------- | -------- | ------------- | ------------------------- |
| Mainnet | P2PK       | Schnorr | `0`     | External | `0`           | `m/44'/111111'/0'/0'/0/0` |
| Mainnet | P2PK       | ECDSA   | `0`     | External | `0`           | `m/44'/111111'/1'/0'/0/0` |
| Testnet | P2PK       | Schnorr | `0`     | External | `0`           | `m/44'/111112'/0'/0'/0/0` |
| Mainnet | Multisig   | Schnorr | `0`     | External | `0`           | `m/45'/111111'/0'/0'/0/0` |
| Mainnet | Multisig   | ECDSA   | `0`     | External | `0`           | `m/45'/111111'/1'/0'/0/0` |
| Testnet | Multisig   | Schnorr | `0`     | External | `0`           | `m/45'/111112'/0'/0'/0/0` |
| Testnet | Multisig   | ECDSA   | `1`     | Internal | `1`           | `m/45'/111112'/1'/1'/1/1` |

### Multisig example

For a three-cosigner mainnet wallet using account `2` and a 2-of-3 policy, Alice and Bob select Schnorr, while Carol selects ECDSA. They provide the following account xpubs:

| Cosigner | Signature scheme | Account xpub origin   |
| -------- | ---------------- | --------------------- |
| Alice    | Schnorr (`0`)    | `m/45'/111111'/0'/2'` |
| Bob      | Schnorr (`0`)    | `m/45'/111111'/0'/2'` |
| Carol    | ECDSA (`1`)      | `m/45'/111111'/1'/2'` |

External address `7` is derived as follows:

```text
Alice's account xpub -> /0/7 -> P_A
Bob's account xpub   -> /0/7 -> P_B
Carol's account xpub -> /0/7 -> P_C
```

Whichever cosigner allocates the address, all three keys use the same suffix. The wallet encodes `P_A` and `P_B` as 32-byte x-only keys and `P_C` as a 33-byte compressed key, then sorts these encodings while retaining each key's signature scheme.

The recorded script construction enforces 2-of-3 using those schemes. Alice and Bob use Schnorr signatures, and Carol uses ECDSA.

## Conformance Vectors

The authoritative machine-readable vectors are in [`kcc-0003/vectors/conformance.json`](kcc-0003/vectors/conformance.json). They cover key derivation, watch-only derivation, multisig key sorting, invalid paths, and independent account discovery.

All byte strings are lowercase hexadecimal. Seeds are public test data and MUST NOT be used for real funds.

## Security Considerations

Sharing an account extended public key exposes its non-hardened descendant public keys to the recipient. Wallets SHOULD treat these keys as sensitive wallet metadata and avoid address reuse to reduce transaction linkage.

BIP32's security considerations apply. In particular, disclosing an account extended public key together with a descendant non-hardened private key can compromise the account's private keys. Hardened boundaries isolate the sibling subtrees, while compromise of the master seed compromises every subtree.

The threat model includes untrusted wallet imports, compromised watch-only services, and cosigners supplying incorrect keys or policy metadata. Wallets rely on correct BIP32 and secp256k1 implementations, secure seed generation and storage, and an agreed multisig policy. Cosigners SHOULD verify the network, account origins, schemes, threshold, and script construction before accepting receiving addresses. Losing or substituting policy metadata can make funds inaccessible or direct funds to a different policy, even when the seed is intact.

The hierarchy separates derived keys. Signature verification, transaction commitments, and any replay protection remain properties of the selected script and network. Path separation alone does not make a transaction safe to sign. Mixed-scheme policies require particular care to preserve each key's scheme through sorting and to apply the matching signature check.

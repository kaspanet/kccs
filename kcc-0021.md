# KCC-0021: Covenant Token Metadata Specification

This specification defines a single JSON metadata object that gives a Kaspa covenant token its display identity: a name, a ticker, a decimals scale, and a verifiable image. It is a sibling to KCC-0020. KCC-0020 defines token behavior (accounting, the transfer interface, and its descriptor artifact); this specification defines identity, discovery, and provenance. It does not modify KCC-0020 and introduces no consensus rules. It describes an off-consensus convention for reading, verifying, and displaying metadata that a covenant deployer commits on chain.

The object is committed once, in the payload of the covenant's genesis (deploy) transaction, so it is immutable at birth and can be consumed with no dependency on any later artifact and with no dependency on a KCC-0020 descriptor being present. That independence is why the convention already works in production today. Field names align with KRC-721 and KRC-20 where the semantics match, so a mixed list of KRC tokens and covenant tokens renders uniformly, and every value is surfaced as a non-unique claim anchored to the canonical Covenant ID.

## Conventions and Terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119. This specification uses the capitalized keywords for normative rigor. Its sibling KCC-0020 expresses the same requirement levels in lowercase prose; the two conventions are equivalent in force.

The following terms are used throughout:

- Covenant instance: a UTXO locked to a covenant program, identified uniquely by its outpoint, as defined in KCC-0001.
- Covenant ID: the KIP-20 identity that descends from a covenant's origin outpoint across its stateful continuations. This is the canonical, unique identity of the asset.
- Genesis (deploy) transaction: the transaction that first creates a covenant instance, that is, the origin of its Covenant ID lineage under KIP-20.
- Metadata object: the single JSON document defined by this specification.
- Consumer: any wallet, explorer, indexer, aggregator, or Reader that parses and displays the metadata object.
- Producer: the deployer, launchpad, or tool that constructs the genesis payload.
- Display claim: an attribute (such as `name` or `ticker`) asserted by the producer that is NOT unique and MUST NOT be treated as an identifier.

## Motivation

A UTXO covenant has no contract storage and no view functions. Unlike an ERC-20 contract it cannot expose `name()`, `symbol()`, or `decimals()`, and unlike an ERC-721 contract it cannot resolve a `tokenURI`. KRC-20 carries only a ticker and a decimals scale and leaves names and logos to off-chain explorers; KRC-721 keeps its per-token metadata off chain behind a base URI. None of these give a covenant token a self-contained, tamper-evident identity record that a consumer can read directly from the chain.

This specification fills that gap with the smallest durable primitive that works: one JSON object placed directly in the covenant's immutable genesis payload. Because that payload lives in an already-confirmed transaction whose bytes can never be rewritten, the record is fixed at birth, needs no indexer registry to exist, and can be read with no dependency on the KCC-0020 descriptor or on any later covenant transition. Pairing an image URL with a SHA-256 commitment lets any verifier prove that the off-chain art is exactly the bytes the deployer committed, so the picture can never be silently swapped after launch. The design goals, in priority order, are reliable reading, parity with KRC field names so mixed lists render uniformly, provenance guarantees a UI can depend on, and rules simple enough that a consumer can implement them correctly on the first try.

## Scope and Discovery

This specification covers reading, verifying, and presenting the metadata of a covenant whose Covenant ID is already known. Discovery is covenant-first: a consumer first identifies a covenant through KIP-20 and KCC-0001 (its program and origin outpoint), then reads that covenant's genesis payload. There is deliberately NO payload-scan discovery path, and this specification defines none: a consumer MUST NOT attempt to enumerate tokens by scanning arbitrary transaction payloads for a metadata shape, because the presence rule (name or ticker) is intentionally weak and would match unrelated JSON. Enumeration of the covenant set is out of scope and is delegated to KCC-0020 recognition and indexer enumeration.

## Relationship to KCC-0001 and KCC-0020

This specification is a sibling of KCC-0020, not a dependency of it, and it MUST NOT modify KCC-0020.

- Identity is the Covenant ID (KCC-0001). A covenant instance is identified uniquely by its outpoint, and its lineage is carried by the Covenant IDs defined by KIP-20. KCC-0020 recognizes the Covenant ID as a covenant identifier type (see KCC-0020). The Covenant ID is therefore the canonical, unique identity of the asset, and this specification adds no identity semantics of its own. Consumers MUST key tokens by Covenant ID and MUST use it as the primary key in all storage, routing, and disambiguation.
- The values in the metadata object (`name`, `ticker`, and the rest) are non-unique display claims layered on top of that identity. They are convenience, not identity. Two distinct covenants MAY commit the same `name` or `ticker`; a consumer MUST NOT resolve, deduplicate, or authenticate a token by any metadata field.
- KCC-0020 is a sibling standard covering behavior. Its descriptor artifact exists to decode covenant state and construct transfers; it is not defined to carry token identity or presentation metadata (see KCC-0020). This specification does not add any field to the KCC-0020 descriptor and does not require a descriptor to exist.
- The genesis payload is the source of truth. A future revision or extension of KCC-0020 MAY reference this metadata object from a descriptor, but any such reference is advisory: on any disagreement between a descriptor reference and the genesis payload, the genesis payload wins, because the payload physically cannot be rewritten whereas a descriptor is later or derived. A consumer that detects a disagreement SHOULD surface a warning but MUST NOT invalidate the token or the payload metadata on that basis.
- Extension precedence. KCC-0020 provides for extended state and extensions. Genesis-payload metadata defined here is authoritative for asset identity and presentation. A KCC-0020 extension MUST NOT redefine the meaning of `name`, `ticker`, `decimals`, `image`, or `image_hash`, and any identity-like value an extension surfaces that disagrees with the genesis payload is advisory only and MUST NOT override it.
- Orthogonality is deliberate: KCC-0001 owns identity, KCC-0020 owns behavior, and this specification owns presentation. A future covenant-NFT specification MAY reuse the `name`, `image`, and `image_hash` shape defined here by omitting the fungible fields (`ticker`, `decimals`), without inheriting fungible accounting.

## Location of the Metadata

The metadata object MUST reside in the `payload` of the covenant's genesis (deploy) transaction: the single transaction that creates the covenant instance whose origin outpoint anchors its Covenant ID lineage under KIP-20.

### Canonical selection

Because a Covenant ID descends from exactly one origin outpoint under KIP-20, the genesis transaction is unique and there is exactly one authoritative payload per Covenant ID. A consumer MUST select that payload by chain-deterministic means and MUST NOT rely on any indexer-local ordering. If an implementation must defensively disambiguate among candidate origin events (for example across a reorg before finality), it MUST break ties by a chain-deterministic key in this order: accepting-block DAA score, then transaction id, then output index. It MUST NOT rely on a private insertion sequence.

### Payload binding

A Kaspa transaction has exactly one payload but MAY create several outputs, so one genesis transaction can instantiate more than one covenant. The metadata object binds to exactly one covenant: when a single genesis transaction creates more than one covenant instance, the metadata object binds to the covenant instance created at the lowest-indexed covenant output of that transaction. A consumer MUST NOT apply the metadata to sibling covenants created by the same transaction at other output indices. Producers SHOULD deploy at most one covenant that carries this metadata per genesis transaction, to avoid ambiguity.

This specification assumes the genesis payload is available to carry the metadata JSON and treats the entire decoded payload as the metadata object. If a future KCC defines additional genesis-payload content that must coexist with this object, that KCC MUST define a delimiting envelope; until then, a payload that does not decode cleanly to a single JSON object per the rules below yields no metadata.

### Size cap

The payload MUST be at most 4096 bytes as it appears on chain. When the hex transport is used (see Encoding and Decoding), this cap applies to the hex string length, not to the decoded JSON, so hex transport roughly halves the usable JSON budget to about 2 KiB. This is ample for the field set defined here. A payload that is empty, or that exceeds 4096 on-chain bytes, yields no metadata (the entire object is treated as absent). The token itself remains valid regardless.

## Encoding and Decoding

The metadata object has exactly one canonical representation: a single UTF-8 JSON object as defined by RFC 8259. There is no second data format. Hexadecimal is a transport encoding of that same UTF-8 JSON, not an alternative schema.

On chain, the payload is one of two transport encodings, both of which decode to the identical UTF-8 JSON object:

1. Plain: the raw UTF-8 bytes of the JSON object. A JSON object begins with `{` (byte `0x7B`), and an object with a first key begins with the bytes `0x7B 0x22` (`{"`).
2. Hex: the ASCII hexadecimal of those same UTF-8 bytes. The hex form of `{"` is the ASCII string `7b22`, so a hex-encoded payload begins with the bytes `0x37 0x62 0x32 0x32`.

### Decode algorithm (normative)

Given the raw payload bytes `raw`, a consumer MUST locate and decode the object as follows:

```text
1. If raw is empty, or len(raw) > 4096, there is no metadata. Stop.
2. Attempt to parse raw as UTF-8 JSON.
   a. If parsing succeeds and the value is a JSON object,
      that object is the candidate. Go to Validation.
   b. If parsing succeeds but the value is not a JSON object
      (array, string, number, boolean, or null),
      there is no metadata. Stop. (Do NOT attempt the hex fallback.)
3. If parsing in step 2 failed, interpret raw as ASCII text,
   trim leading and trailing ASCII whitespace, and hex-decode it.
   a. If hex-decoding fails, there is no metadata. Stop.
4. Attempt to parse the hex-decoded bytes as UTF-8 JSON.
   a. If the result is a JSON object, it is the candidate. Go to Validation.
   b. Otherwise, there is no metadata. Stop.
```

The plain path is attempted first; the hex path is the fallback and is only tried when the plain parse fails outright. The decoded top-level value MUST be a JSON object: an array, scalar, or null yields no metadata. The two leading-byte signatures (`{"` versus `7b22`) make the transport unambiguous, but a consumer is NOT required to sniff them; attempting plain-then-hex as above is sufficient and normative. Consumers MUST trim ASCII whitespace before hex-decoding.

## The Metadata Object

The normative schema, in the pseudo-struct style of KCC-0020:

```text
CovenantTokenMetadata {
    name:       string  | none   # display name,            <= 48 code points
    ticker:     string  | none   # short symbol,            <= 12 code points
    decimals:   integer | string | none   # display scale,  0 to 255, default 0
    image:      string  | none   # https:// or ipfs:// URI, <= 256 code points
    image_hash: string  | none   # sha256 of image bytes, 64 hex chars
}
```

All string length limits are measured in Unicode scalar values (code points), not bytes and not UTF-16 code units. String values MUST be trimmed of leading and trailing whitespace and MUST NOT contain control characters or the format and default-ignorable characters called out under Validation and Failure Modes; a value that violates its own constraint is dropped, and its sibling fields are kept.

| Field | JSON type | Presence | Constraint |
|-------|-----------|----------|------------|
| `name` | string | at least one of `name`, `ticker` REQUIRED; `name` RECOMMENDED | at most 48 code points |
| `ticker` | string | at least one of `name`, `ticker` REQUIRED | at most 12 code points; read-alias `symbol` |
| `decimals` | integer or base-10 string | OPTIONAL, default 0 | 0 to 255; display only |
| `image` | string | OPTIONAL | at most 256 code points; scheme `https://` or `ipfs://` |
| `image_hash` | string | OPTIONAL | 64 hexadecimal characters, any case, normalized to lowercase |

### Field definitions

- `name` (string, RECOMMENDED). The human display name, at most 48 code points, non-empty after trimming. Aligns with ERC-721 and KRC-721 `name`. A non-unique display claim.

- `ticker` (string, OPTIONAL; read-alias `symbol`). The short ticker or symbol, at most 12 code points. `symbol` is the ERC-20 field name and is accepted as a read alias, which buys ERC-20 tooling parity. Producers SHOULD write `ticker`. Precedence applies among valid values only: if both `ticker` and `symbol` are present and valid, `ticker` wins; if the `ticker` value is present but invalid (for example longer than 12 code points), a valid `symbol` is used instead. Unlike KRC-20's `tick`, this value carries NO uniqueness rule and NO 4-to-6-character floor: a covenant ticker is a non-unique display claim, not a registered identifier.

- `decimals` (integer or string, OPTIONAL, default 0). A display-only rendering scalar: a consumer divides the displayed base-unit amount by 10 raised to the power `decimals` for presentation only. `decimals` MUST NOT affect on-chain accounting, which is always in exact base units; this specification does not touch the KCC-0020 amount representation. To interoperate with both integer-emitting producers and the string-valued convention KRC-20 uses for `dec`, `decimals` MAY be committed as a JSON integer or as a JSON string containing a base-10 unsigned integer, and a consumer MUST accept both and coerce to an integer. The permitted range is 0 to 255 inclusive, matching ERC-20's `uint8` decimals type (the widest range any comparable standard uses); a value outside that range, a non-integer, or a non-numeric string MUST be ignored, falling back to the default 0. Absent means 0 (an integer-unit token). Note that KRC-20 defaults its `dec` to 8 while this specification defaults to 0, because covenant accounting is in base units; a producer that wants KRC-20-style 8-decimal rendering MUST state `decimals` explicitly. Producers SHOULD always emit `decimals` explicitly to remove ambiguity in mixed KRC and covenant lists. Consumers SHOULD treat an absent `decimals` on a covenant token presented beside KRC-20 tokens as a WARN-level condition rather than silently assuming a value.

- `image` (string, OPTIONAL). A URI for the token image, at most 256 code points. The scheme MUST be `https://` (a location plus hash, see Image Pinning) or `ipfs://` (content-addressed). Any other scheme, including `http://` and `data:`, MUST be rejected at parse and the field dropped, so that a non-conforming scheme can never reach the fetch pipeline. Aligns in name with ERC-721 and KRC-721 `image`, and deliberately diverges from KRC-721's IPFS-only policy by additionally allowing HTTPS paired with `image_hash`.

- `image_hash` (string, OPTIONAL). The hexadecimal SHA-256 of the exact image bytes (see Image Pinning), 64 hexadecimal characters. Uppercase input is valid: a consumer accepts any-case 64-hex and normalizes it to lowercase before comparison. A value that is not exactly 64 hexadecimal characters is dropped (a malformed hash is treated as no hash). This field has no KRC or ERC precedent: it re-creates, for an HTTPS URL, the integrity that an IPFS CID provides natively. It is OPTIONAL for object validity; it is REQUIRED to obtain served, verified art from an `https://` image.

Fields that belong to asset behavior rather than identity are explicitly out of scope and MUST NOT appear here as normative fields: KRC-20's `max`, `lim`, and `pre` (supply and mint policy) live in the KCC-0020 domain and MUST NOT be interpreted from this object.

## Field Alignment with KRC and ERC Standards

This mapping lets a consumer render KRC and covenant tokens in one uniform list.

| This specification | KRC-721 | KRC-20 | ERC-20 / ERC-721 | Alignment |
|--------------------|---------|--------|------------------|-----------|
| `name` | `name` | (none) | `name` | Identical; kept verbatim. |
| `ticker` (alias `symbol`) | `tick` (collection) | `tick` | `symbol` | Same concept, different spelling. NOT unique here; KRC-20's 4-to-6-character and first-deploy-wins rules are deliberately NOT imported. |
| `decimals` | (none) | `dec` (default 8) | `decimals` | Same concept, spelled out. Accepts integer or string. Default 0 here, display only. |
| `image` | `image` (ipfs only) | (none) | `image` | Same field. `https://` is additionally allowed here (paired with `image_hash`). |
| `image_hash` | (none) | (none) | (none) | New. The `https://` counterpart of what an `ipfs://` CID provides for free. |

KRC-20 commits `tick` and `dec` as its on-chain keys. This specification does not read `tick` or `dec`: a consumer that also parses KRC-20 payloads MUST apply a per-protocol mapping (`tick` to `ticker`, `dec` to `decimals`) rather than assume covenant payloads carry KRC-20 keys. The alignment above is at the level of rendered fields, not on-chain key names.

## Reserved and Optional Fields

To prepare the shape for a future covenant-NFT sibling and to aid tooling, the following keys are RESERVED. They are not normative fields of this version, and the reference Reader does not parse them. Producers MAY include them; consumers MUST ignore any they do not understand and MUST NOT reject the object because of them.

- `description`, `external_url`, `attributes`: reserved for a future covenant-NFT specification, which is expected to reuse the ERC-721 and OpenSea shapes verbatim (`description` as free text, `external_url` as an HTTPS project link, and `attributes` as an array of `{ trait_type, value, display_type }` objects with `value` of type string or number). This version does not define their bounds or semantics.
- `p`, `v`: an OPTIONAL protocol tag and version hint. A producer MAY set `p` to `"kcc-0021"` and `v` to a version string to aid payload-level routing and future breaking-change detection. Because existing deploys predate these keys, a consumer MUST NOT gate recognition on them and MUST recognize a valid object that omits them.

## JSON Schema

The following JSON Schema (draft 2020-12) is a partial validator for the canonical object. It expresses field types, bounds, and the presence rule. It cannot express the cross-field image-pinning rules, the whitespace-trim and character-set rejection rules, the scheme restriction, the `ticker` and `symbol` precedence, or the `decimals` string coercion; all of those remain governed by the prose above. No `$id` is declared, and the schema is not published at any URL; it is reproduced here for reference only.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "KCC-0021 Covenant Token Metadata",
  "type": "object",
  "properties": {
    "name":       { "type": "string", "minLength": 1, "maxLength": 48 },
    "ticker":     { "type": "string", "minLength": 1, "maxLength": 12 },
    "symbol":     { "type": "string", "minLength": 1, "maxLength": 12 },
    "decimals":   {
      "oneOf": [
        { "type": "integer", "minimum": 0, "maximum": 255 },
        { "type": "string", "pattern": "^[0-9]{1,3}$" }
      ]
    },
    "image":      { "type": "string", "maxLength": 256,
                    "pattern": "^(https|ipfs)://.+" },
    "image_hash": { "type": "string", "pattern": "^[0-9a-fA-F]{64}$" }
  },
  "anyOf": [
    { "required": ["name"] },
    { "required": ["ticker"] },
    { "required": ["symbol"] }
  ],
  "additionalProperties": true
}
```

`additionalProperties` is `true` by design: unknown and reserved fields are ignored, not rejected (see Validation and Failure Modes). The `image_hash` pattern is deliberately case-insensitive; consumers normalize the value to lowercase before comparison.

## Image Pinning and Verification

A covenant commits a reference (a URI, and for HTTPS a hash), never the image bytes themselves, so the image lives off chain and could rot or be substituted. This specification defines two pinning modes so that a verifier can prove the off-chain bytes are the ones the deployer committed at birth. Neither mode is mandated over the other.

### Mode 1: location plus hash (https), fully specified

`image` is an `https://` URL and `image_hash` is the lowercase-normalized hexadecimal SHA-256 of the exact image bytes. This mode is fully specified here and is the mode the reference Reader fetches, verifies, and serves.

What the hash covers: the decoded representation body, that is, the image bytes after any HTTP `Content-Encoding` (such as gzip or br) has been removed, which are the bytes an image decoder would see. The commitment is `image_hash = lowercase_hex(SHA-256(decoded_image_bytes))`. To keep the proof deterministic across consumers, a consumer SHOULD request `Accept-Encoding: identity` and MUST hash the decoded representation body if a content encoding is nonetheless applied; it MUST NOT hash the compressed wire bytes. A consumer MUST fetch the full representation and MUST NOT use a Range or partial request for verification.

An `https://` image with no valid `image_hash` MUST NOT be fetched or served as verified art. It MAY be surfaced as a labeled external link only, and MUST NOT be presented as the token's authenticated art. Committing the hash is mandatory to receive served art in this mode.

Fetch and verification pipeline (a consumer that fetches and serves art MUST apply all of it):

```text
1. Require both image and image_hash. An https image with no valid
   image_hash is a link claim only: it is never fetched or served as art.

2. Scheme. The fetched scheme MUST be https. (http was rejected at parse.)

3. SSRF preflight. Reject the request if the host, or any address it
   resolves to, is loopback, RFC1918 private, link-local (including
   169.254/16 cloud metadata), unspecified, broadcast, 0.0.0.0/8,
   CGNAT 100.64/10, 192.0.0.0/24, or the IPv6 equivalents (loopback,
   unspecified, fc00::/7 unique-local, fe80::/10 link-local). A literal
   IP host is checked directly; a named host is resolved and EVERY
   resolved address MUST be public. An IPv4-mapped IPv6 address inherits
   the IPv4 verdict.

4. Redirects. Limiting the redirect COUNT does not bound the redirect
   TARGET. A consumer MUST either (a) disable redirect following and
   treat any 3xx as art-unavailable (RECOMMENDED), or (b) re-run the
   full SSRF preflight of step 3 against each redirect Location before
   connecting to it, up to a small hop limit. A consumer MUST NOT follow
   a redirect to an address that has not passed the preflight.

5. Rebind backstop. The address vetted in step 3 SHOULD be the address
   actually connected to (resolve once, then dial that pinned IP with
   the original Host and SNI). Where the fetcher re-resolves independently,
   a network egress policy that blocks the ranges in step 3 from the
   fetcher is a REQUIRED backstop, because a DNS rebind between the
   preflight and the fetch can otherwise reach an internal target.

6. Bounded fetch. Enforce a total timeout (reference: 10 seconds), a
   redirect-hop bound consistent with step 4, and a body cap on the
   DECODED bytes (reference: 2 MiB) so a compressed bomb cannot exceed
   it. A non-2xx status, a timeout, or an over-cap body is a fetch failure.

7. The pin. lowercase_hex(SHA-256(decoded_body)) MUST equal image_hash.

8. Format sniff. Determine the content type by sniffing the leading
   bytes (at least 12), never by trusting the origin Content-Type header.
   Only PNG, JPEG, GIF, and WEBP are recognized as servable images.

9. Serve. On success, serve the sniffed content type with
   X-Content-Type-Options: nosniff, and MAY cache immutably
   (reference: Cache-Control: public, max-age=86400, immutable).
```

### Mode 2: content-addressed (ipfs), claim in this version

`image` is an `ipfs://<cid>[/path]` URI. The Content Identifier (CID) embeds a multihash of the referenced content, so an `ipfs://` URI is self-pinning: integrity holds ONLY if the consumer re-derives the CID's multihash from the fetched bytes and compares it to the CID. A gateway fetch that renders whatever the gateway returns, without recomputing and matching the CID, is UNVERIFIED and MUST be labeled as such. A consumer MUST NOT present gateway-returned bytes as pinned or verified art unless it has performed CID verification.

This version does not specify a normative IPFS gateway-resolution and serving pipeline (gateway selection, applying the SSRF guard to the gateway host, path resolution, size caps, and multihash re-derivation). The reference Reader does not resolve, verify, or serve IPFS today; it surfaces an `ipfs://` value as an unverified claim link. Full content-addressed serving is RECOMMENDED practice and is expected to be specified in a future revision. Because the CID is the integrity anchor for this mode, `image_hash` SHOULD be omitted when `image` is `ipfs://`; a general IPFS CID multihash is not equal to `SHA-256` over the byte sequence a gateway returns (unixfs wrapping, chunking, or a non-sha2-256 multihash), so an `image_hash` paired with an `ipfs://` URI is advisory only and MUST NOT by itself cause a consumer to withhold otherwise CID-verified art.

### Outcomes

Failure of the art NEVER invalidates the token or its text metadata:

- Verified: the bytes MAY be served and cached immutably.
- Hash mismatch (Mode 1): the consumer MUST NOT display the fetched bytes (they are unverified or substituted) but MUST keep the token and all of its text metadata. A mismatch invalidates the art, never the token.
- Unreachable, over cap, SSRF-rejected, or not a recognized image format: the art is unavailable; the consumer MUST keep the token, SHOULD show a placeholder, and MAY retry later.

### Immutability and negative caching

Because the hash is committed in the immutable genesis payload, a verified image is immutable in practice: to change the picture, the URL would have to start serving different bytes, and those bytes would then fail the same hash. The art can never be silently swapped after launch. Only a VERIFIED result is immutable. Negative results (fetch failure, mismatch) MUST remain retryable and SHOULD use bounded backoff rather than a single long fixed TTL, so that a transient failure or a hostile responder at first contact cannot deny correct art for a full window. The reference Reader negative-caches fetch failures for about 1 hour and mismatches for about 24 hours; consumers MAY use similar windows but SHOULD prefer backoff for availability.

## Mutability

The metadata object MUST be committed in the genesis payload and MUST NOT be overridable by any later covenant transition. Consumers MUST treat the genesis payload as canonical even if a later artifact (including a KCC-0020 descriptor reference) disagrees. The commitment is what is immutable; the off-chain image bytes referenced by `image` MAY become unreachable over time, but they can never be substituted for different bytes, because any replacement must still satisfy the committed `image_hash` (Mode 1) or the committed CID (Mode 2).

There is no mutable variant in this version. Any future evolvable-metadata mechanism belongs in a separate extension specification in which the genesis payload still serves as the canonical fallback; it is out of scope here.

## Validation and Failure Modes

Validation governs safe rendering, not consensus. The metadata is an untrusted deployer claim surfaced with provenance, so a consumer shows what is safe, drops what is not, and never lets a bad claim invalidate the on-chain token. The overarching rules are: the object fails closed to no metadata; individual bad fields fail soft (drop the field, keep its siblings); a bad claim NEVER invalidates the on-chain token.

Object level (fail closed):

- Top-level type: the decoded value MUST be a JSON object. An array, scalar, or null yields no metadata.
- Presence: the object is present only if, after per-field validation, it carries at least one valid value among `name`, `ticker`, or its alias `symbol`. `name` is RECOMMENDED but not strictly required. An object with only `image` or `image_hash`, and no valid `name` or `ticker`, is NOT recognized and yields no metadata. (A future covenant-NFT sibling is expected to relax this presence rule to allow image-only objects; consumers MUST NOT hard-code name-or-ticker as a universal covenant-metadata recognition test beyond this fungible specification.)
- Oversize or empty: a payload over 4096 on-chain bytes, or an empty payload, yields no metadata; the token stays valid.
- Unknown or extra fields: consumers MUST ignore them and MUST NOT reject the object. This is the forward-compatibility contract that lets future revisions and vendor keys coexist with today's parsers.
- Duplicate keys: producers MUST NOT emit duplicate JSON keys. Consumer behavior on a duplicate key is otherwise undefined beyond the requirement not to crash; consumers SHOULD take the last value, per common JSON parser behavior.

Field level (fail soft):

- Each string field MUST be a JSON string; a value of any other JSON type is ignored for that field, with the sole exception of `decimals`, which MAY be a JSON integer or a base-10 JSON string.
- String fields MUST be trimmed of leading and trailing whitespace, MUST be non-empty after trimming, and MUST NOT contain control characters (Unicode category Cc). For display safety, consumers MUST additionally reject or strip bidirectional format controls (U+202A through U+202E and U+2066 through U+2069) and zero-width and default-ignorable characters (Unicode category Cf), which neither Cc filtering nor NFC normalization removes.
- Lengths are counted in Unicode scalar values (code points).
- `image_hash`: after trimming it MUST be exactly 64 ASCII hexadecimal digits of any case; consumers normalize to lowercase before comparison. Anything else is dropped.
- `decimals`: MUST resolve to an integer in 0 to 255; otherwise ignored (default 0).
- `image`: MUST use scheme `https://` or `ipfs://`; otherwise dropped.
- A field that violates its type, bound, character-set, or scheme constraint is dropped while its sibling fields are kept.

Non-uniqueness:

- Duplicate `name` or `ticker` values across different covenants are explicitly ALLOWED. Consumers MUST NOT key on them, MUST surface them as claims with provenance, and MUST disambiguate by Covenant ID.
- Values are UTF-8 strings. NFC normalization is RECOMMENDED for display. Key ordering is insignificant, and consumers MUST NOT depend on it. This specification imposes NO canonical byte serialization on the object, because the object is never itself re-hashed; only the image bytes are hashed, via `image_hash`.

## Consumer Conformance

A conforming consumer (aggregator, wallet, explorer, or indexer):

- MUST use the Covenant ID as the primary key for every token, and MUST NOT use `name` or `ticker` as a key.
- MUST read the metadata object only from the canonical genesis payload selected by the chain-deterministic rule, decoding plain-then-hex as specified, and MUST NOT require a KCC-0020 descriptor to be present.
- MUST require the decoded top-level value to be a JSON object and MUST apply the presence rule.
- MUST surface metadata as claims with provenance, not as facts, keeping them distinct from the canonical Covenant-ID-derived identity, which a claim never overrides.
- MUST default `decimals` to 0 when absent, MUST treat `decimals` as display only, and MUST NOT let it affect accounting.
- MUST NOT display fetched image bytes in Mode 1 unless `lowercase_hex(SHA-256(decoded_body))` equals `image_hash`, MUST derive the content type from the sniffed bytes, and MUST serve verified art from the re-hosted verified bytes rather than by hotlinking the origin URL.
- MUST NOT present `ipfs://` gateway bytes as verified art without recomputing and matching the CID.
- MUST apply the SSRF preflight, the redirect rule, and the size and time bounds before any fetch, and MUST NOT follow a redirect to an unvetted address.
- MUST reject or strip control, bidirectional-format, and zero-width characters from displayed strings, and SHOULD render the Covenant ID in a directional isolation context so a claimed name cannot reorder surrounding UI.
- MUST ignore unknown fields and MUST keep the token when any single field or the whole object is invalid.
- That renders a covenant AS a fungible token MUST independently confirm KCC-0020 conformance; metadata presence alone is NOT evidence of token behavior, and `decimals` applies only once KCC-0020 conformance is established. UIs SHOULD label metadata-only covenants distinctly from verified KCC-0020 tokens.

## Producer Conformance

A conforming producer:

- MUST commit exactly one metadata object in the genesis payload, at most 4096 on-chain bytes, as plain or hex-encoded UTF-8 JSON.
- MUST include at least one valid `name` or `ticker`.
- SHOULD emit `decimals` explicitly; MAY emit it as a base-10 string for compatibility with string-only Readers.
- For a hash-pinned image, MUST publish an `https://` URL whose exact decoded bytes hash to the committed `image_hash`, and SHOULD keep those bytes hosted so the art stays servable. Alternatively MAY use a self-pinning `ipfs://` URI and omit `image_hash`.
- MUST use only PNG, JPEG, GIF, or WEBP for pinned art. SVG is deliberately excluded (see Security and Provenance Considerations); committing any other format yields a valid token whose art is simply unavailable.
- MUST NOT expect any value in this object to confer uniqueness; identity is the Covenant ID.

## Security and Provenance Considerations

- Claims, not facts. Every value here is an unauthenticated statement by the deployer. Uniqueness comes only from the Covenant ID. A UI that presents a claimed name or ticker as if it were canonical identity invites impersonation; surface provenance and disambiguate by Covenant ID. Consumers SHOULD attach claims under namespaced keys and stamp their source; the reference Reader uses `claimed_name`, `claimed_ticker`, `claimed_image`, and `claimed_image_hash`, and sets `metadata_source: "genesis_payload"` whenever any claim exists, keeping the canonical name a separate primary field a claim never overrides.
- Impersonation is not only exact collision. Because names and tickers are non-unique display claims, a hostile deployer can commit a string that is visually identical to a well-known token using homoglyphs (for example a Cyrillic character in an otherwise Latin ticker), bidirectional overrides (U+202E and the isolates U+2066 through U+2069), or zero-width and default-ignorable characters. Stripping only control characters (category Cc) and applying NFC does NOT catch these. Consumers MUST reject or strip bidirectional-format and category-Cf characters, SHOULD run confusable or skeleton checks against known tickers before presenting a claim as trusted, and MUST render Covenant IDs in a directional isolation context so a claimed name cannot reorder surrounding UI.
- Server-side request forgery. The image URL is attacker-controlled. The SSRF preflight alone is not a complete control: limiting the redirect count does not bound the redirect target, and a DNS rebind between the preflight and the fetch can reach an internal address. Consumers MUST therefore apply the redirect rule (disable redirects or re-vet every hop) and MUST either pin the connection to the vetted address or run behind a network egress policy that blocks the private, link-local, and cloud-metadata ranges from the fetcher. Host resolution alone MUST NOT be presented as a complete SSRF control.
- Do not trust the origin content type. The served content type MUST come from magic-byte sniffing of the verified bytes, not from the origin header, and MUST be served with `X-Content-Type-Options: nosniff`. Only PNG, JPEG, GIF, and WEBP are accepted. This closes the case where the hash matches but the bytes are HTML, SVG, or an executable payload; SVG is excluded specifically because it can carry script.
- Denial of service. The fetch MUST be timeout-bounded, redirect-bounded, and capped on the decoded body size so that a compressed bomb cannot exceed the cap. Availability griefing is asymmetric: substitution is prevented by the pin, but a transient hostile responder at first contact can seed a negative result, so negative results MUST remain retryable with bounded backoff rather than a single long TTL.
- Integrity model. In Mode 1 the hash is the trust anchor: mismatched bytes are withheld while the token stays intact. In Mode 2 the CID is the trust anchor and is meaningful only if re-derived from the fetched bytes. Neither mode weakens the on-chain token, whose identity and accounting are independent of the picture. Transport (HTTPS) is not the integrity anchor; the hash or CID is.
- Token-ness is not implied by metadata. Presence of `name` or `ticker` in a genesis payload does NOT establish that a covenant has KCC-0020 fungible-token behavior. A consumer that lists a covenant as a token MUST independently confirm KCC-0020 conformance, and `decimals` applies only once that is established.

## Backwards Compatibility

This specification formalizes a convention that is already deployed and enforced in production, so backwards compatibility is a first-class concern.

- Existing tokens conform as-is. Every covenant deployed before this KCC that carried a valid `name`, `ticker`, `image`, or `image_hash` in its genesis payload remains conforming without change. No on-chain migration and no redeploy is required.
- Added semantics are additive. `decimals` is newly consumable, the `https://` and `ipfs://` scheme restriction, the redirect and rebind hardening, and the bidirectional and zero-width character rejection tighten how consumers read and fetch; none of them changes what is already committed on chain. Already verified and served art, and existing positive and negative image caches, remain valid.
- `decimals` on existing tokens. No token on chain today carries a consumable `decimals`: the reference parser reads only string-valued fields and never read `decimals` at all, so existing tokens render as `decimals = 0` by construction. This specification resolves the type question going forward by accepting integer or base-10 string, so that a string `decimals` a future producer commits is consumable even by string-oriented Readers.
- Known reference divergences to be tightened. The reference Reader currently (a) permits `http://` at its fetch guard, whereas this specification requires `https://` for served art and rejects `http://` at parse; (b) follows up to 3 redirects without re-vetting each hop; (c) strips only control characters (Cc) and not bidirectional-format or zero-width characters; (d) does not yet parse `decimals`; and (e) does not resolve, verify, or serve `ipfs://` art. On each of these points the reference is more permissive or less complete than this specification and is expected to be tightened. Existing tokens remain valid across every one of these changes.

## Versioning and Extensibility

This specification carries no mandatory version field. Extensibility is achieved by the ignore-unknown-fields rule: a later revision MAY add OPTIONAL fields, and vendors MAY add namespaced keys, without breaking existing consumers, provided they do not repurpose the reserved keys defined here (`name`, `ticker`, `symbol`, `decimals`, `image`, `image_hash`, and the reserved `description`, `external_url`, `attributes`, `p`, `v`). A producer MAY set the OPTIONAL `p` (`"kcc-0021"`) and `v` hints to aid payload-level routing and breaking-change detection, but consumers MUST NOT require them. A change that would alter the meaning of an existing field, or that would require a mutable commitment, is a breaking change and MUST be published as a separate KCC rather than as a silent reinterpretation of this one. A future covenant-NFT specification is expected to reuse the `name`, `image`, `image_hash`, and `attributes` shape defined here, omitting `ticker` and `decimals`, so that identity tooling built for this specification works unchanged for non-fungible covenants.

## Worked Examples

An HTTPS image pinned by hash. The canonical UTF-8 JSON object:

```json
{
  "name": "Kaspa Rocket",
  "ticker": "ROCK",
  "decimals": "8",
  "image": "https://cdn.example.org/rock.png",
  "image_hash": "3b8c4e0f2a1d6b9c7e5f4a2d8b0c1e3f6a9d2c5b8e1f4a7d0c3b6e9f2a5d8c1b"
}
```

Committed in the plain transport, the payload bytes are exactly those UTF-8 bytes. Committed in the hex transport, the same object is the ASCII hex of those bytes, beginning `7b226e616d65` (the hex of `{"name`); a consumer detects the failed plain parse, hex-decodes, and parses the identical object. A consumer verifying the art requests `Accept-Encoding: identity`, fetches the URL under the SSRF and redirect rules, confirms `SHA-256(decoded_body)` equals the committed hash, sniffs the bytes as PNG, and serves them immutably with `X-Content-Type-Options: nosniff`; a wallet that has independently confirmed KCC-0020 conformance renders a balance of `100000000` base units as `1.00000000 ROCK`.

A content-addressed image needs no hash, because the CID pins the bytes:

```json
{
  "name": "Pixel Crow",
  "ticker": "CROW",
  "decimals": 0,
  "image": "ipfs://bafybeigdyrzt5sfp7udm7hu76uh7y26nf3efuylqabf3oclgtqy55fbzdi"
}
```

A minimal valid object (name only) is recognized metadata:

```json
{ "name": "Kaspa Rocket" }
```

## Test Vectors

These vectors are normative. Each pairs a raw payload with the expected parsed result or the exact reason it yields no metadata. Hex strings are the raw payload bytes; where a plain and a hex transport are both shown, they decode to the identical object.

Positive, minimal, plain transport:

```text
raw (plain UTF-8) : {"name":"KAS"}
raw (hex bytes)   : 7b226e616d65223a224b4153227d
result            : { name: "KAS" }  (recognized; ticker/image/image_hash absent)
```

Positive, minimal, hex transport (same object):

```text
raw (on-chain ASCII) : 7b226e616d65223a224b4153227d
first bytes          : 37 62 32 32   (ASCII "7b22")
decode               : plain parse fails, hex-decode succeeds, parse succeeds
result               : { name: "KAS" }
```

Positive, full object, plain transport:

```text
raw (plain UTF-8) : {"name":"Kaspa Rocket","ticker":"ROCK","decimals":"8",
                     "image":"https://cdn.example.org/rock.png",
                     "image_hash":"3b8c4e0f2a1d6b9c7e5f4a2d8b0c1e3f6a9d2c5b8e1f4a7d0c3b6e9f2a5d8c1b"}
result            : { name:"Kaspa Rocket", ticker:"ROCK", decimals:8,
                     image:"https://cdn.example.org/rock.png",
                     image_hash:"3b8c...8c1b" }
```

Negative, top-level JSON array (not an object):

```text
raw (plain UTF-8) : ["name","KAS"]
first byte        : 5b   ("[")
result            : no metadata (top-level value is not an object;
                     hex fallback is NOT attempted because plain parse succeeded)
```

Negative, presence rule (image and hash only, no name or ticker):

```text
raw (plain UTF-8) : {"image":"https://x/y.png","image_hash":"3b8c...8c1b"}
result            : no metadata (fails name-or-ticker presence rule)
```

Field normalization and drop cases (object still recognized via a valid name):

```text
{"name":"KAS","image_hash":"3B8C4E0F2A1D6B9C7E5F4A2D8B0C1E3F6A9D2C5B8E1F4A7D0C3B6E9F2A5D8C1B"}
  -> image_hash accepted (uppercase input), normalized to lowercase.

{"name":"KAS","decimals":8}     -> decimals = 8 (integer form).
{"name":"KAS","decimals":"8"}   -> decimals = 8 (string form coerced).
{"name":"KAS","decimals":300}   -> decimals dropped, default 0 (out of 0..255).
{"name":"KAS","image":"http://x/y.png"} -> image dropped (scheme not https/ipfs).
{"name":"KAS","ticker":"THIS_TICKER_IS_TOO_LONG","symbol":"OK"}
  -> ticker invalid (over 12 code points), falls through to symbol -> ticker = "OK".
{"name":"KAS","image_hash":"zz...(non-hex)"} -> image_hash dropped; token kept.
```

Negative, oversize:

```text
raw : any payload whose on-chain length exceeds 4096 bytes
result : no metadata (the token remains valid)
```

## Reference Implementation and Acknowledgments

The reference Reader for this convention is kascov, which parses the genesis payload (`claimed_token_meta`) and fetches, hash-verifies, and serves pinned art (`token_image_handler`) as described above. As of this draft the reference Reader consumes `name`, `ticker` (with the `symbol` alias), `image`, and `image_hash`; it does not yet consume `decimals` or the reserved fields, and its known divergences are listed under Backwards Compatibility. A conforming Reader that renders balances MUST apply `decimals` (reading it as a JSON integer or a base-10 string); Readers that display identity only MAY ignore it.

This convention was first surfaced in the KasSmiths "Asset Standards" discussion, where feedback from Andreas shaped the sibling-standard framing and several of the design choices; the reference implementation is kascov, and the first launchpad to adopt it at deploy time was KaspaRocket. Authorship of this specification and its status are recorded in the README index row rather than in the document body, per repository convention.

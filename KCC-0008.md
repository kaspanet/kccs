# KCC-0008: Multi-Token Standard

| Field | Value |
|-------|-------|
| **KCC** | 0008 |
| **Category** | Asset Standard |
| **Title** | Multi-Token Standard |
| **Author** | Vida Wallet |
| **Status** | Draft |
| **Created** | 2026-07-25 |

## Abstract

A single covenant supporting fungible tokens, non-fungible tokens, or both from one deployment. Every `token_id` carries a `token_kind` field that determines its semantics. This standard defines one interface and one state layout for every token type on Kaspa, building on the transfer convention established by KCC-0020.

## Motivation

Prior ecosystems adopted separate standards for fungible and non-fungible tokens, then a third to unify them, because each was created after the preceding one proved insufficient. Kaspa does not need to retrace that path. A single standard at inception means developer tooling — wallets, DEXes, indexers — integrates once.

## Specification

### State Layout

Every KCC-0008 covenant state begins with the following fields, in this order and encoding:

```
offset  size    field           encoding
0       8       token_id        uint64, big-endian
8       1       token_kind      byte
9       1       flags           byte
10      32      owner_id        bytes32
42      8       amount          uint64, big-endian
50      64      metadata_uri    padded bytes64, UTF-8
114     32      extended_digest bytes32
```

Total: 146 bytes of standard header.

**token_kind** values:

```
FUNGIBLE      = 0x00  // amount denotes balance; many holders per token_id
NON_FUNGIBLE  = 0x01  // amount always 1; single holder per token_id
```

**flags** bitfield:

```
BIT_FROZEN  = 0x01  // all transfers blocked
BIT_MINTED  = 0x02  // token_id has been fully minted
BIT_BURNED  = 0x04  // token_id has been burned (terminal state)
```

**metadata_uri** specifies an off-chain metadata resource for the token (name, ticker, decimals, image). For non-fungible tokens this references the specific token. For fungible tokens it references the token class. See KCC-0021 for canonical metadata layout.

**extended_digest** commits to covenant-specific data beyond the standard header. Computed as:

```
extended_digest = blake2b(encode(extended_state))
```

Token-specific transitions may update extended state. The standard transfer entrypoints treat extended state as opaque and preserve its digest unchanged across inputs who share the same `token_id`.

### Core Entrypoints

#### transfer

```
transfer(
    State[] next_states,     // successor states, ordered by covenant output index
    Sig[]   signatures,       // authorization signatures, positional
    byte[]  witnesses         // per-input metadata
)
```

`transfer` is invoked by the first covenant input as the leader entrypoint. It validates the complete state transition for one or more `token_id` values. Remaining covenant inputs invoke `transfer_delegator` (no input data) to join the transfer declared by the leader.

Rules enforced:

1. For each `token_id` in consumed states: `sum(prev_amounts) == sum(next_amounts)` — no implicit minting or burning.
2. `token_id` and `token_kind` are immutable for each consumed covenant state.
3. For non-fungible states (`token_kind == NON_FUNGIBLE`): `amount == 1` in both input and output.
4. For each consumed input where `witnesses[i] != BORROWED_RECEIVE`: `signatures[i]` must be a valid signature over the transaction sighash by the owner identified by `owner_id` and `token_kind`.
5. `BIT_FROZEN` must not be set on any consumed state.
6. `BIT_BURNED` must not be set on any consumed state.

For the Borrowed Receive extension (witness value `0xFF`), see KCC-0020 Section "KCC20 Borrowed Receive Extension v1". This standard adopts that extension: `witnesses[i] == 0xFF` exempts that input from owner authorization, and the successor state must preserve `owner_id`, `token_kind`, `metadata_uri`, and `extended_digest` while increasing `amount`.

#### transfer_delegator

```
transfer_delegator()
```

Invoked by every non-leader covenant input. Delegates to the leader's `transfer` entrypoint. Enforces that at least one input invoked `transfer` as leader.

#### mint

```
mint(
    uint64  token_id,
    byte    token_kind,
    uint64  amount,
    bytes64 metadata_uri,
    bytes32 extended_digest
)
```

Creates new token supply. Caller must be the covenant owner (see KCC-0001 for owner identification). Rules:

1. `token_id` must not already exist in the covenant state (no reuse).
2. If `token_kind == NON_FUNGIBLE`: `amount` must equal 1.
3. If `token_kind == FUNGIBLE`: `amount` may be any value up to the configured `max_supply` for this `token_id`.
4. On success, a new UTXO is produced with the standard state header populated as specified, `flags = BIT_MINTED`, and the covenant owner as initial `owner_id`.

#### mint_batch

```
mint_batch(
    MintParams[] tokens     // array of {token_id, token_kind, amount, metadata_uri, extended_digest}
)
```

Atomic batch mint. All tokens are created or none are. Same rules as `mint` apply per token.

#### burn

```
burn(
    uint64 token_id,
    uint64 amount
)
```

Destroys tokens. Caller must be the holder. Rules:

1. Caller's balance for `token_id` must be ≥ `amount`.
2. On success, the burned state's `flags` is set to `BIT_BURNED`. The state UTXO remains but is unspendable.

For non-fungible tokens (`token_kind == NON_FUNGIBLE`): `amount` is ignored; the entire token is burned.

### Fungible Extensions

#### approve

```
approve(
    bytes32 spender_id,
    uint64  token_id,
    uint64  amount,
    uint64  expires_block
)
```

Authorizes a spender to transfer up to `amount` of `token_id` on behalf of the caller. Rules:

1. Overwrites any prior allowance for `(caller, spender, token_id)` — preventing the allowance double-spend issue documented in ERC-20.
2. `expires_block` must be > current block height.

Allowance state is stored in a companion covenant with fields:

```
offset  size    field
0       32      holder_id       bytes32
32      32      spender_id      bytes32
64      8       token_id        uint64
72      8       amount          uint64
80      8       expires_block   uint64
```

#### transfer_from

```
transfer_from(
    bytes32 holder_id,
    bytes32 spender_id,
    uint64  token_id,
    uint64  amount,
    State[] next_states,
    Sig[]   signatures,
    byte[]  witnesses
)
```

Spender transfers on behalf of holder. Extends `transfer` semantics with allowance validation. Rules:

1. An allowance must exist for `(holder_id, spender_id, token_id)` with `allowance >= amount` and `expires_block > current_block`.
2. After transfer, the allowance is reduced by `amount`.
3. Spender's `signatures[i]` authorizes the transfer.

### Non-Fungible Extensions

#### set_metadata

```
set_metadata(
    uint64  token_id,
    bytes64 metadata_uri
)
```

Updates the metadata URI for a non-fungible token. Caller must be the current holder. Only valid when `token_kind == NON_FUNGIBLE`.

#### set_royalty

```
set_royalty(
    uint64  token_id,
    bytes32 recipient_id,
    uint16  bps                // 500 = 5%
)
```

Configures a royalty recipient and rate for secondary sales. Rules:

1. Only valid when `token_kind == NON_FUNGIBLE`.
2. `bps` must be ≤ 10000 (100%).
3. Immutable after first call for a given `token_id`.

### Owner Actions

#### set_token_config

```
set_token_config(
    uint64 token_id,
    uint64 max_supply,          // 0 = uncapped
    uint64 mint_expiry_block    // 0 = never expires
)
```

Configures supply caps and mint window for a `token_id`. Caller must be the covenant owner. Rules:

1. May only be set once per `token_id` — immutable after configuration.
2. `max_supply` applies to fungible tokens only.

#### freeze / unfreeze

```
freeze()
unfreeze()
```

Pauses or resumes all transfers. Caller must be the covenant owner. Sets/clears `BIT_FROZEN` on the covenant-level state.

#### transfer_ownership

```
transfer_ownership(
    bytes32 new_owner_id
)
```

Transfers the covenant owner role. Caller must be the current owner.

### Descriptor

Each KCC-0008 covenant must publish a descriptor:

```
KCC0008Descriptor {
    prefix: bytes              // covenant script bytes before mutable state
    suffix: bytes              // covenant script bytes after mutable state
    token_ids: uint64[]        // token_ids managed by this deployment
    multi_token_mode: enum     // SINGLE | MULTI — whether one token_id or many
    kcc20_extensions: ExtensionId[]  // supported extensions (e.g., Borrowed Receive)
}
```

The descriptor allows wallets and indexers to identify the covenant, decode its state, and determine which token types and extensions it supports.

### Witness Semantics

Witness values for the `transfer` entrypoint:

```
BORROWED_RECEIVE  = 0xFF   // KCC-0020 Borrowed Receive (exempts authorization)
STANDARD_TRANSFER = 0x00   // normal signed transfer
```

For `transfer_delegator`, witnesses are not used.

For `mint`, `burn`, `approve`, and owner actions, witnesses correspond to standard authorization — the caller provides `signatures[i]` authorizing the state transition.

### KCC-0020 Alignment

This standard adopts the following from KCC-0020:

- **Transfer interface**: leader/delegator pattern with `transfer(State[], Sig[], byte[])` entrypoint signature
- **Positional input/output pairing**: consumed state at index `i` corresponds to successor state at index `i`
- **Witness semantics**: positional witness values determine authorization mode
- **Borrowed Receive**: `witnesses[i] == 0xFF` exempts input from owner authorization while preserving `owner_id`, `token_kind`, `extended_digest`
- **Extended state**: opaque `extended_digest` commitment via blake2b
- **Descriptor**: `prefix/suffix` covenant script bytes for template identification

Where this standard extends KCC-0020:

- **token_kind** field distinguishes fungible from non-fungible within the same state layout
- **Multi-token semantics**: multiple `token_id` values in one deployment
- **Mint/burn**: supply creation and destruction
- **Allowance system**: approve/transfer_from with companion covenant
- **NFT-specific extensions**: metadata URI, royalties
- **Owner controls**: freeze, supply caps, ownership transfer

## Encoding

This standard specifies the semantic interface and extended state layout for multi-token covenants. For the byte-level encoding of the transfer leader/delegator pattern, witness positional semantics, and Borrowed Receive extension, see KCC-0020 (Fungible Token Covenant Specification by Manyfest, Michael Sutton, and IzioDev). For metadata identity and discovery, see KCC-0021 (Knitser).

## Profiles

Wallets and DEXes detect token behavior from `token_kind`:

| Profile | Detection | Entrypoints |
|---------|-----------|-------------|
| **Fungible** | `token_kind = 0x00` | transfer, approve, transfer_from, mint, burn |
| **Non-Fungible** | `token_kind = 0x01, amount = 1` | transfer, set_metadata, set_royalty, burn |

A single deployment may use both profiles — e.g., a game issuing fungible currency (token_id=0, kind=0x00) and non-fungible items (token_id=1, kind=0x01) from the same covenant.

## Rules

1. `token_id` must be unique and immutable within a deployment.
2. `token_kind` is immutable for each minted `token_id`.
3. Non-fungible tokens must have `amount == 1` in all valid states.
4. `approve` must overwrite, not add to, any existing allowance.
5. `transfer` must preserve the input/output sum for each `token_id`.
6. `mint` fails if `total_supply + amount > max_supply` when `max_supply ≠ 0`.
7. Royalty `bps` is immutable after the first `set_royalty` call.
8. All state-changing entrypoints fail while `BIT_FROZEN` is set.
9. `BIT_BURNED` states are terminal — no further transitions permitted.
10. The descriptor must be published before any wallet or indexer can interact with the covenant.

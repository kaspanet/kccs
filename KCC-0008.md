# KCC-0008: Multi-Token Standard

| Field | Value |
|-------|-------|
| **KCC** | 0008 |
| **Category** | Asset Standard |
| **Title** | Multi-Token Standard |
| **Author** | Vida Wallet |
| **Status** | Draft |
| **Created** | 2026-07-25 |

## Abstract

A single covenant that manages fungible tokens, non-fungible tokens, or both in one deployment. Each `token_id` carries a `fungible` flag that determines its behavior. This proposal defines one interface for every token type on Kaspa.

## Motivation

Prior ecosystems adopted separate standards for fungible and non-fungible tokens, then a third to unify them, because each was created after the preceding one proved insufficient. Kaspa does not need to retrace that path. A single standard from the start means developers deploy once, wallets integrate once, and DEXes support every token through one interface.

## Specification

### Core Entrypoints

| # | Entrypoint | Caller | Description |
|---|-----------|--------|-------------|
| 1 | `mint` | Owner | Create tokens of `token_id`. Amount > 1 = fungible. Amount = 1 = non-fungible. |
| 2 | `mint_batch` | Owner | Create multiple token types in one transaction. |
| 3 | `transfer` | Holder | Send `amount` of `token_id` to recipient. |
| 4 | `transfer_batch` | Holder | Transfer multiple token types atomically. |
| 5 | `burn` | Holder | Destroy `amount` of `token_id`. |

### Fungible Extensions

| # | Entrypoint | Description |
|---|-----------|-------------|
| 6 | `approve` | Authorize `spender` for `amount` of `token_id`. Overwrites any prior allowance. |
| 7 | `transfer_from` | Spender transfers on behalf of holder. Requires sufficient, unexpired allowance. |

### Non-Fungible Extensions

| # | Entrypoint | Description |
|---|-----------|-------------|
| 8 | `set_uri` | Attach a metadata URI to a token. |
| 9 | `set_royalty` | Configure a royalty recipient and basis points for a token type. |

### Owner Actions

| # | Entrypoint | Description |
|---|-----------|-------------|
| 10 | `freeze` | Pause all transfers. |
| 11 | `unfreeze` | Resume transfers. |
| 12 | `transfer_ownership` | Transfer the owner role. |

## State

```
tokens: [{
  id               uint64
  fungible         bool         // true = many holders, false = single owner
  supply           uint64       // tokens minted so far
  max_supply       uint64       // 0 = uncapped
  name             bytes32
  symbol           bytes32      // empty for non-fungible
  decimals         uint8        // fungible only; typically 8
  uri              bytes32      // non-fungible only
  royalty_recipient pubkey      // non-fungible only
  royalty_bps      uint16       // non-fungible only; 500 = 5%
}]

owner              pubkey
frozen             bool
```

## Balance Model

### Fungible

Each holder's balance is a covenant UTXO carrying the holder's public key and amount in its state. A transfer consumes one or more sender UTXOs and produces one or more recipient UTXOs. The covenant enforces that input and output amounts for a given `token_id` are equal — no implicit minting or burning.

### Non-Fungible

Each token is a single UTXO. Transferring a token consumes the existing UTXO and produces a new one with the new owner.

### Allowances

Allowances are recorded in a companion covenant with fields `{holder, spender, token_id, amount, expires}`. `approve` creates or overwrites an allowance. `transfer_from` checks the allowance exists, is sufficient, and is unexpired. Overwriting rather than adding prevents the allowance double-spend issue documented in ERC-20.

## Profiles

Wallets and DEXes detect token behavior from the `fungible` flag:

| Profile | Detection | Interface |
|---------|-----------|-----------|
| **Fungible** | `fungible = true` | transfer, approve, transfer_from, mint, burn |
| **Non-Fungible** | `fungible = false, supply = 1` | transfer, set_uri, set_royalty, burn |

A single deployment may mix profiles — a game issues fungible currency and non-fungible items from the same covenant.

## Rules

1. `token_id` must be unique within a deployment.
2. Non-fungible tokens must have `supply = 1`.
3. `approve` must overwrite, not add to, any existing allowance.
4. `transfer` must preserve the input/output sum for each `token_id`.
5. `mint` fails if `supply + amount > max_supply` when `max_supply ≠ 0`.
6. Royalties are immutable after the first `set_royalty`.
7. All state-changing operations fail while `frozen = true`.

# KCC-0008: Multi-Token Standard

| Field | Value |
|-------|-------|
| **KCC** | 0008 |
| **Category** | Asset Standard |
| **Title** | Multi-Token Standard |
| **Author** | Vida Wallet |
| **Status** | Draft |
| **Created** | 2026-07-25 |
| **Depends on** | KCC-0020 (PR #2, draft), KCC-0001 (PR #3, draft) |

## Abstract

A single covenant supporting fungible tokens, non-fungible tokens, or both from one deployment. Every `token_id` carries a `token_kind` field that determines its semantics. This standard defines one interface and one state layout for every token type on Kaspa, building on the transfer convention established by KCC-0020.

## Motivation

Prior ecosystems adopted separate standards for fungible and non-fungible tokens, then a third to unify them, because each was created after the preceding one proved insufficient. Kaspa does not need to retrace that path. A single standard at inception means developer tooling — wallets, DEXes, indexers — integrates once. KCC-0020 defines the transfer convention (Reader/Writer roles, leader/delegator pattern, Borrowed Receive) and leaves as open questions how to address mint, burn, freeze, pause, and supply management. KCC-0008 answers those questions within the same covenant framework, providing a complete token lifecycle without fragmenting the ecosystem into separate standards for fungible and non-fungible assets.

## Specification

### State Layout

Every KCC-0008 covenant state begins with the following fields, in this order and encoding:

```
offset  size    field               encoding
0       8       token_id            uint64, big-endian
8       1       token_kind          byte
9       1       flags               byte
10      32      owner_id            bytes32
42      1       identifier_type     byte
43      8       amount              uint64, big-endian
51      64      metadata_uri        padded bytes64, UTF-8
115     32      extended_state_digest     bytes32
```

Total: 147 bytes of standard header.

Note: This header extends KCC-0020's 3-field layout (ownerIdentifier + identifierType + amount). The fields `token_id`, `token_kind`, `flags`, `metadata_uri`, and `extended_state_digest` are additions on top of the KCC-0020 base. This means a KCC-0008-aware reader can extract the KCC-0020 fields (owner and amount) by reading offsets 10–50. A plain KCC-0020 reader that expects fields at offset 0 will NOT correctly decode KCC-0008 states without explicit awareness of the offset shift. Implementations MUST advertise their covenant type (KCC-0008 vs KCC-0020) so readers select the correct offset layout.

**identifier_type** values:

```
PUBKEY       = 0x00  // owner_id is a public key hash
SCRIPT_HASH  = 0x01  // owner_id is a script hash
COVENANT_ID  = 0x02  // owner_id identifies another covenant
```

Note: `identifier_type` maps to the control principal concept defined in KCC-0002 (IzioDev). KCC-0002 defines profiles including `p2pkh-schnorr/v1`, `p2pkh-ecdsa/v1`, `covenant_id`, and `program_hash`. KCC-0008 adopts the simpler 3-type model for compatibility with KCC-0020's `identifierType` field. Implementations requiring richer principal typing should reference KCC-0002.

**token_kind** values:

```
FUNGIBLE      = 0x00  // amount denotes balance; many holders per token_id
NON_FUNGIBLE  = 0x01  // amount always 1; single holder per token_id
```

**flags** bitfield:

```
BIT_BURNED  = 0x01  // token_id has been burned (terminal state)
```

`BIT_MINTED` (0x02) is reserved but not used in the standard header. For non-fungible tokens, implementers may use it in extended state to mark an individual token UTXO as the original mint.

**metadata_uri** specifies an off-chain metadata resource for the token (name, ticker, decimals, image). For non-fungible tokens this references the specific token. For fungible tokens it references the token class. The URI points to a JSON document containing `name`, `symbol`, `decimals`, and `image` fields. See KCC-0021 (adopted by kascov and KaspaRocket) for the canonical metadata format. For fungible tokens, `metadata_uri` is replicated across all holder UTXOs; implementations may deduplicate via an off-chain registry.

**extended_state_digest** commits to covenant-specific data beyond the standard header. Computed as:

```
extended_state_digest = blake2b(encode(extended_state))
```

Token-specific transitions may update extended state. The standard transfer entrypoints treat extended state as opaque and preserve its digest unchanged across inputs who share the same `token_id`.

### Core Entrypoints

#### transfer

```
transfer(
    State[] newStates,     // successor states, ordered by covenant output index
    sig[] sigs,       // authorization signatures, positional
    byte[]  witnesses         // per-input metadata
)
```

`transfer` is invoked by the first covenant input as the leader entrypoint. It validates the complete state transition for one or more `token_id` values. Remaining covenant inputs invoke `transfer_delegator` (no input data) to join the transfer declared by the leader.

The SilverScript declaration per KCC-0020 includes `prevStates` explicitly:
```silverscript
function transfer(State[] prevStates, State[] newStates, sig[] sigs, byte[] witnesses)
```
This specification describes the leader's sigscript arguments (`newStates`, `sigs`, `witnesses`). In SilverScript, `prevStates` are bound from the consumed covenant UTXOs via `#[covenant(binding = cov, from = maxCovIns)]` and are not passed as sigscript arguments. The Reader reconstructs `prevStates` from the UTXO set; the Writer declares `newStates` in the sigscript.

Rules enforced:

1. For each `token_id` in consumed states: `sum(prev_amounts) == sum(next_amounts)` — no implicit minting or burning.
2. `token_id` and `token_kind` are immutable for each consumed covenant state.
3. For non-fungible states (`token_kind == NON_FUNGIBLE`): `amount == 1` in both input and output.
4. For each consumed input where `witnesses[i] != BORROWED_RECEIVE`: `sigs[i]` must be a valid signature over the transaction sighash by the owner identified by `owner_id` and `token_kind`.
5. The token configuration `frozen` flag must be `0x00` for each consumed state's `token_id`. The flag is stored in the Token Configuration Extended State (see above).
6. `BIT_BURNED` must not be set on any consumed state.
7. If multiple consumed states of the same `token_id` have different `extended_state_digest` values, the transfer MUST fail.

For the Borrowed Receive extension (witness value `0xFF`), see KCC-0020 Section "KCC20 Borrowed Receive Extension v1". This standard adopts that extension: `witnesses[i] == 0xFF` exempts that input from owner authorization, and the successor state must preserve `owner_id`, `identifier_type`, `token_kind`, `metadata_uri`, and `extended_state_digest` while increasing `amount`. Note: Borrowed Receive does not apply to non-fungible tokens (`token_kind == NON_FUNGIBLE`) because NFTs have `amount == 1` and cannot be increased.

#### transfer_delegator

```
transfer_delegator()
```

Invoked by every non-leader covenant input. Delegates to the leader's `transfer` entrypoint. Enforces that at least one input invoked `transfer` as leader.

#### mint

```
mint(
    uint64  token_id,
    byte    token_kind,
    uint64  amount,
    bytes64 metadata_uri,
    bytes32 extended_state_digest
)
```

Creates new token supply. Caller must be the covenant owner. The owner is identified by a covenant-specific owner public key stored in the deployment descriptor. Rules:

1. `token_id` must not already exist in the covenant state (no reuse).
2. If `token_kind == NON_FUNGIBLE`: `amount` must equal 1.
3. If `token_kind == FUNGIBLE`: `amount` may be any value up to the configured `max_supply` for this `token_id`.
4. On success, a new UTXO is produced with the standard state header populated as specified and the covenant owner as initial `owner_id`. `total_supply` for this `token_id` is incremented by `amount`. The extended state is committed via `extended_state_digest`.

#### mint_batch

```
mint_batch(
    MintParams[] tokens     // array of {token_id, token_kind, amount, metadata_uri, extended_state_digest}
)
```

Atomic batch mint. All tokens are created or none are. Same rules as `mint` apply per token.

#### burn

```
burn(
    uint64 token_id,
    uint64 amount
)
```

Destroys tokens. Caller must be the holder. `total_supply` for `token_id` is decremented by the burned amount. Rules:

1. Caller's balance for `token_id` must be ≥ `amount`.
2. On success, the `BIT_BURNED` flag is set in the burned state's `flags` (flags = flags | BIT_BURNED). The state UTXO remains but is unspendable.

For non-fungible tokens (`token_kind == NON_FUNGIBLE`): `amount` must be 1; any other value is rejected. The entire token is burned.

### Fungible Extensions

#### approve

```
approve(
    bytes32 spender_id,
    uint64  token_id,
    uint64  amount,
    uint64  expires_block
)
```

Authorizes a spender to transfer up to `amount` of `token_id` on behalf of the caller. Rules:

1. Overwrites any prior allowance for `(caller, spender, token_id)` — preventing the allowance double-spend issue documented in ERC-20.
2. `expires_block` must be > current block height.

Allowance state is stored in a companion covenant deployed separately from the token covenant. A single allowance covenant may serve multiple KCC-0008 token deployments. The allowance covenant's address is published in the KCC-0008 deployment descriptor (`allowance_covenant` field).

The allowance covenant stores one UTXO per `(holder_id, spender_id, token_id)` tuple with the following state layout:

```
offset  size    field
0       32      holder_id       bytes32
32      32      spender_id      bytes32
64      8       token_id        uint64
72      8       amount          uint64
80      8       expires_block   uint64
```

#### transfer_from

```
transfer_from(
    bytes32 holder_id,
    bytes32 spender_id,
    uint64  token_id,
    uint64  amount,
    State[] newStates,
    sig[] sigs,
    byte[]  witnesses
)
```

Spender transfers on behalf of holder. Extends `transfer` semantics with allowance validation. Rules:

1. An allowance must exist for `(holder_id, spender_id, token_id)` with `allowance >= amount` and `expires_block > current_block`.
2. After transfer, the allowance is reduced by `amount`.
3. Spender's `sigs[i]` authorizes the transfer.

### Non-Fungible Extensions

#### set_metadata

```
set_metadata(
    uint64  token_id,
    bytes64 metadata_uri
)
```

Updates the metadata URI for a non-fungible token. Caller must be the current holder. Only valid when `token_kind == NON_FUNGIBLE`.

#### set_royalty

```
set_royalty(
    uint64  token_id,
    bytes32 recipient_id,
    uint16  bps                // 500 = 5%
)
```

Configures a royalty recipient and rate for secondary sales. Rules:

1. Only valid when `token_kind == NON_FUNGIBLE`.
2. `bps` must be ≤ 10000 (100%).
3. Immutable after first call for a given `token_id`.

### Owner Actions

#### set_token_config

```
set_token_config(
    uint64 token_id,
    uint64 max_supply,          // 0 = uncapped
    uint64 mint_expiry_block    // 0 = never expires
)
```

Configures supply caps and mint window for a `token_id`. Caller must be the covenant owner. Rules:

1. May only be set once per `token_id` — immutable after configuration.
2. `max_supply` applies to fungible tokens only.

#### freeze / unfreeze

```
freeze(uint64 token_id)
unfreeze(uint64 token_id)
```

Pauses or resumes transfers for `token_id`. Caller must be the covenant owner. The frozen state is covenant-level (not per-UTXO) — a single freeze flag per `token_id` gates all transfers of that token type. `freeze` and `unfreeze` are always callable by the covenant owner and not themselves gated by the frozen state.

#### transfer_ownership

```
transfer_ownership(
    bytes32 new_owner_id
)
```

Transfers the covenant owner role. Caller must be the current owner.

### Token Configuration Extended State

Every `token_id` that has been configured via `set_token_config` has a 24-byte configuration committed via `extended_state_digest`:

```
offset  size    field               encoding
0       8       max_supply          uint64, big-endian (0 = uncapped)
8       8       mint_expiry_block   uint64, big-endian (0 = never expires)
16      8       total_supply        uint64, big-endian (tokens minted so far)
24      1       frozen              byte (0x00 = active, 0x01 = frozen)
25      7       reserved            zero-filled
```

Total: 32 bytes of token configuration.

If `set_token_config` has never been called for a `token_id`, all fields default to 0 (uncapped, never expires, zero supply, not frozen). A `max_supply` of 0 means no supply cap.

**`total_supply`** is updated atomically on every `mint` (increment) and `burn` (decrement). It is stored in the covenant's configuration state, not per-UTXO — `mint` and `burn` write the new value; all other entrypoints read it for enforcement.

**`frozen`** gates all token-state-changing entrypoints (transfer, mint, mint_batch, burn, approve, transfer_from). When `frozen == 0x01`, these entrypoints fail. `freeze` sets it; `unfreeze` clears it. Both are always callable by the covenant owner.

### Royalty Configuration Extended State

When `set_royalty` is called for a non-fungible `token_id`, the following sub-layout is committed via `extended_state_digest`:

```
offset  size    field           encoding
0       32      recipient_id    bytes32
32      2       bps             uint16, big-endian
```

Immutability: the covenant rejects any `set_royalty` call where the royalty portion of `extended_state_digest` is non-zero and differs from the previous value.

### Descriptor

Each KCC-0008 covenant must publish a descriptor:

```
KCC0008Descriptor {
    prefix: bytes              // covenant script bytes before mutable state
    suffix: bytes              // covenant script bytes after mutable state
    state_layout: FieldDef[]   // field-by-field description of the 147-byte header
    token_ids: uint64[]        // token_ids managed by this deployment
    multi_token_mode: uint8    // 0x00 = SINGLE, 0x01 = MULTI
    leader_entrypoint: uint8   // compiled entrypoint selector for transfer
    delegator_entrypoint: uint8 // compiled entrypoint selector for transfer_delegator
    allowance_covenant: bytes32 // covenant address of the allowance companion (zero if unused)
    optional_extensions: ExtensionId[]  // supported extensions
}
```

The descriptor allows wallets and indexers to identify the covenant, decode its state, and determine which token types and extensions it supports.

### Witness Semantics

Witness values for the `transfer` entrypoint:

```
BORROWED_RECEIVE  = 0xFF   // KCC-0020 Borrowed Receive (exempts authorization)
STANDARD_TRANSFER = 0x00   // normal signed transfer
```

For `transfer_delegator`, witnesses are not used.

For `mint`, `burn`, `approve`, and owner actions, witnesses correspond to standard authorization — the caller provides `sigs[i]` authorizing the state transition.

### KCC-0020 Alignment

This standard adopts the following from KCC-0020:

- **Transfer interface**: leader/delegator pattern with `transfer(State[], sig[], byte[])` entrypoint signature
- **Positional input/output pairing**: consumed state at index `i` corresponds to successor state at index `i`
- **Witness semantics**: positional witness values determine authorization mode
- **Borrowed Receive**: `witnesses[i] == 0xFF` exempts input from owner authorization while preserving `owner_id`, `identifier_type`, `token_kind`, `extended_state_digest`. Not applicable to non-fungible tokens.
- **Extended state**: opaque `extended_state_digest` commitment via blake2b
- **Descriptor**: `prefix/suffix` covenant script bytes, plus `state_layout`, `leader_entrypoint`, and `delegator_entrypoint` selectors for KCC-0020 reader/writer compatibility

Where this standard extends KCC-0020:

- **State header**: KCC-0008's 147-byte header is a superset of KCC-0020's 3-field header. Fields not in KCC-0020: `token_id`, `token_kind`, `flags`, `metadata_uri`. KCC-0020's `ownerIdentifier` maps to `owner_id`; `identifierType` maps to `identifier_type`.
- **token_kind** field distinguishes fungible from non-fungible within the same state layout
- **Multi-token semantics**: multiple `token_id` values in one deployment
- **Mint/burn**: supply creation and destruction
- **Allowance system**: approve/transfer_from with companion covenant
- **NFT-specific extensions**: metadata URI, royalties
- **Owner controls**: freeze, supply caps, ownership transfer

## Encoding

This standard specifies the semantic interface and extended state layout for multi-token covenants. For the byte-level encoding of the transfer leader/delegator pattern, witness positional semantics, and Borrowed Receive extension, see KCC-0020. For metadata identity and discovery, see KCC-0021 (Knitser).

## Profiles

Wallets and DEXes detect token behavior from `token_kind`:

| Profile | Detection | Entrypoints |
|---------|-----------|-------------|
| **Fungible** | `token_kind = 0x00` | transfer, approve, transfer_from, mint, burn |
| **Non-Fungible** | `token_kind = 0x01, amount = 1` | transfer, set_metadata, set_royalty, burn |

A single deployment may use both profiles — e.g., a game issuing fungible currency (token_id=0, kind=0x00) and non-fungible items (token_id=1, kind=0x01) from the same covenant.

## Rules

1. `token_id` must be unique and immutable within a deployment.
2. `token_kind` is immutable for each minted `token_id`.
3. Non-fungible tokens must have `amount == 1` in all valid states.
4. `approve` must overwrite, not add to, any existing allowance.
5. `transfer` must preserve the input/output sum for each `token_id`.
6. `mint` fails if `total_supply + amount > max_supply` when `max_supply ≠ 0`. If `max_supply` has not been configured (default 0), there is no supply cap.
7. Royalty `bps` is immutable after the first `set_royalty` call.
8. All token-state-changing entrypoints (transfer, mint, mint_batch, burn, approve, transfer_from) fail while the `frozen` flag is `0x01` in the Token Configuration Extended State for the relevant `token_id`. `freeze` and `unfreeze` are exempt — always callable by the covenant owner.
9. `BIT_BURNED` states are terminal — no further transitions permitted.
10. The descriptor must be published before any wallet or indexer can interact with the covenant.

The author maintains a conforming implementation. This document defines the convention; an implementation demonstrates conformance.

## Implementation Notes

### Metadata URI Replication

For fungible tokens with many holders, the 64-byte `metadata_uri` is replicated across every holder's UTXO. This is deliberate: any single UTXO is self-describing without external lookups. Implementations may optimize indexing via a metadata registry, but the covenant guarantees every UTXO independently carries the canonical URI.

### KCC-0020 Reader Compatibility

A KCC-0020-compliant reader can decode owner and amount from any KCC-0008 state by reading offsets 10–50 (owner_id + identifier_type + amount). The remaining bytes (0–9, 51–146) are opaque extension data to a KCC-0020 reader. Multi-token-aware tooling reads the full 147-byte header.
## Ecosystem Status

KCC-0020 token transfers are live on Kaspa mainnet via kascov (kascov.io) — the first KCC20-compatible wallet. KCC-0021 metadata is adopted by kascov and KaspaRocket. KCC-0402 payment channels are mainnet-proven. KCC-0008 is designed to compose with this existing ecosystem, extending the KCC-0020 transfer layer with full token lifecycle management.

This specification defines the convention. A conforming SilverScript implementation is under development. Until published, the byte-level state layouts, entrypoint signatures, and rules in this document serve as the implementer's reference.

# Sutton-Level Review: KCC-0009, 0010, 0011

**Reviewer**: Subagent, reviewing against KCC-0020 (Sutton/Manyfest/IzioDev, PR #2)  
**Standard**: KCC-0020 defines an *interface-level* spec — byte offsets are NOT specified; state is `owner_identifier + identifier_type + amount + extended_state_digest` with no sizes or encodings beyond field-level types.  
**Date**: 2026-07-25

---

## KCC-0020 FACTS (ground truth)

KCC-0020 does NOT have:
- Byte-level offset tables (no `offset  size  field  encoding`)
- `token_id`, `token_kind`, `flags`, `metadata_uri` fields
- `owner_id` (it uses `owner_identifier`)
- `extended_digest` (it uses `extended_state_digest`)
- Token profiles, mint/burn, approve/transfer_from, royalties, owner controls

KCC-0020 DOES have:
- `owner_identifier` (bytes32), `identifier_type` (byte: 0x00/0x01/0x02), `amount` (integer), `extended_state_digest` (bytes32)
- `transfer(State[], sig[], byte[])` + `transfer_delegator()`
- `BORROWED_RECEIVE = 0xFF` extension
- `extended_state_digest = blake2b(encode(extended_state))`
- `KCC20Descriptor { prefix, suffix, extended_state_layout, kcc20_extensions }`

## KCC-0009: GOVERNED TOKEN

### BLOCKERS

**B1. MISSING ✓/✗ FEATURE TABLE — Line 332 (KCC-0020 Alignment section)**
KCC-0009 has NO standard `transfer(State[], Sig[], byte[])` entrypoint. Per `standards-writing/references/non-transfer-spec-encoding.md`: "If a spec has no standard transfer entrypoint at all... KCC-0020 Alignment must include a ✓/✗ table documenting what is NOT adopted." KCC-0008-quality-template says "This is the single most valuable artifact for core dev review." KCC-0009 has prose under "Where this standard diverges" (lines 340-347) but NO summary table. Sutton will want the table. KCC-0008's precedent shows a structured KCC-0020 Alignment with clear adopt/extend separation — KCC-0009 should have the ✓/✗ table per non-transfer-spec-encoding.md.

**B2. WRONG FIELD NAME REFERENCE — Line 338**
`"analogous to KCC-0020's extended_digest"` — KCC-0020 calls this field `extended_state_digest`, not `extended_digest`. `extended_digest` is KCC-0008's term. In a section titled "KCC-0020 Alignment," using **KCC-0008's** field name to describe **KCC-0020's** concept is incorrect. Sutton co-authored KCC-0020 and will catch this instantly.

**B3. METADATA_URI CLAIMED AS KCC-0020 ADOPTION — Lines 337-338**
"Metadata URI: metadata_uri field (bytes64, UTF-8 padded) for off-chain token identity. See KCC-0021..." — KCC-0020 has NO `metadata_uri` field in its state layout. Zero. This is a KCC-0008 addition. The KCC-0020 Alignment section lists this under "adopts the following from KCC-0020" which is factually wrong. It should be listed under "adopts from KCC-0008" or as a KCC-0009 extension.

**B4. DESCRIPTOR PATTERN CLAIM IS SHALLOW — Line 336**
"Descriptor pattern: prefix/suffix covenant script bytes for template identification" — KCC-0020's descriptor is `{prefix, suffix, extended_state_layout, kcc20_extensions}`. KCC-0009's descriptor is `{prefix, suffix, num_governors, quorum, veto_power, proposal_timeout, execution_delay, governor_set_digest, metadata_uri}`. These are fundamentally different — KCC-0009 adds 7 fields KCC-0020 never had and drops 2 fields (extended_state_layout, kcc20_extensions) KCC-0020 expected. Saying you "adopt" the pattern when you change every field but prefix/suffix is misleading. This should say "extends" or "adapts."

### MAJOR ISSUES

**M1. STATE LAYOUT HAS NO KCC-0020 FIELDS — Lines 46-57**
KCC-0020 requires `owner_identifier + identifier_type + amount + extended_state_digest`. KCC-0009's config state has `num_governors, quorum, flags, reserved, proposal_timeout, execution_delay, next_proposal_id, metadata_uri, total_supply, treasury_balance`. None of KCC-0020's fields appear. This is acknowledged in divergence, but the Encoding section (line 370) claims "The encoding is self-contained — implementers do not need to reference KCC-0020 for field layout or entrypoint signatures." Yet the KCC-0020 Alignment section claims adoption of multiple KCC-0020 features. If the encoding is self-contained, what exactly is being adopted? The relationship is unclear.

**M2. PROPOSAL STATES HAVE NO KCC-0020 FIELDS EITHER — Lines 88-103**
Proposal state has `proposal_id, proposal_type, proposer, recipient, amount, governor_index, new_governor, reason_hash, created_block, expires_block, executes_after, approval_count, veto_count, status`. Again, zero KCC-0020 fields. The "amount" field exists but at offset 73 (uint64 BE) — KCC-0020's `amount` is an `integer` type without specified byte encoding. Completely incompatible.

**M3. MULTI-PARTY SIGNATURE MODEL NOT DOCUMENTED IN WITNESS SEMANTICS — Lines 312-330**
Witness semantics table says `propose`, `second`, `veto` each get "governor's authorization signature" as `witness[0]`. But KCC-0009's governance model has N governors — which governor? How is the governor resolved from the signature? Lines 326-327 say "The governor's index in governors[] is resolved by matching the pubkey hash." This means every entrypoint must: (a) recover the pubkey from the signature, (b) hash it, and (c) scan governors[] for a match. This is O(N) per entrypoint call. For a standard with `N` potentially large (line 46: `num_governors` is uint8, up to 255), that's a legitimate gas concern. KCC-0020's witness model is O(1) positional. KCC-0009 should address this complexity explicitly.

**M4. EXECUTE ENTRYPOINT IS PERMISSIONLESS — Line 319**
"execute: caller authorization (may be empty — anyone can execute)" — KCC-0020 has no concept of a permissionless entrypoint. Every KCC-0020 entrypoint either has signer auth or is the Borrowed Receive extension. KCC-0009 should document that execute is a novel authorization model (no signature required) and explain why this doesn't create a griefing vector (someone could execute earlier than the proposer intended if execution_delay is zero; though rule 6 handles this for zero-delay, what about non-zero delay where someone front-runs the proposer?).

**M5. MISSING FORMULA SECTION**
KCC-0008-quality-template says: "When the standard involves on-chain computation... include a dedicated section with precise mathematical formulas." KCC-0009 has implicit computation (quorum reached when `approval_count >= quorum`, `executes_after = current_block + execution_delay`) but no formula section. The proposer auto-approve logic in rule 3 (line 388) says "The proposer's auto-approval counts toward quorum" but this is described in prose, not a formula. A formula like `can_execute(P) = (P.approval_count >= quorum) ∧ (current_block ≥ P.executes_after) ∧ (current_block < P.expires_block) ∧ (P.status == PENDING)` would add Sutton-level precision.

**M6. NO PER-DISCRIMINATOR ENCODING TABLE FOR PROPOSAL STATE — Lines 136-142**
The table "Field usage by proposal_type" lists which fields are used/unused for TRANSFER vs REPLACE_GOVERNOR but doesn't show the actual byte encoding per type. Per KCC-0008-quality-template: for union fields where byte interpretation depends on an enum, "include a secondary encoding table showing how the bytes are interpreted per discriminator value." The fields `recipient` (offset 41-73, unused for REPLACE_GOVERNOR) and `governor_index` (offset 81-89, unused for TRANSFER) should have explicit "zero-filled" statements per type.

### MINOR ISSUES

**m1. Line 50**: `metadata_uri` type is `padded bytes64, UTF-8` — KCC-0020 has no metadata_uri field. KCC-0008 uses bytes64 too, but this is a KCC-0008 convention, not KCC-0020.

**m2. Line 55**: `total_supply: uint64, big-endian` — values up to 18,446,744,073,709,551,615. Fine for most tokens, but no discussion of overflow behavior for mint (rule 14: bypass governance). If owner can mint arbitrarily, `total_supply` could overflow uint64.

**m3. Line 147 (mint entrypoint)**: Signature is `mint(uint64 amount, bytes32 recipient)` — but the "Caller must be the covenant owner (see KCC-0001 for owner identification)". How does KCC-0001 identify the owner? KCC-0001 is also unpublished. This is a cross-reference to thin air.

**m4. Line 277 (burn entrypoint)**: `burn(uint64 amount)` — burns from treasury only. What if someone wants to burn their own held tokens? No owner-level burn. Intentional design choice, but not stated.

**m5. Line 402**: "Companion standards" lists KCC-0001, KCC-0020, KCC-0021, KCC-0008. None of these are merged to kaspanet/kccs main. Per KCC skill rules: "No references to unpublished standards." If these are submitted in dependency order (KCC-0020 → KCC-0008 → then KCC-0009), this is fine, but the reference list should honestly note the dependency chain.

**m6. Line 306**: Descriptor field `governor_set_digest: bytes32` — "blake2b of packed governors[]". In which order? Ascending by pubkey hash? By array index? Must be explicit.

**m7. No `Updated` field with proper date format** — metadata table has `Updated: 2026-07-25` on line 11, which is fine.

## KCC-0010: FEE-ON-TRANSFER TOKEN

This is the strongest of the three. Has explicit formulas, honest KCC-0020/KCC-0008 separation, clear byte-level layout.

### BLOCKERS

*None at blocker level. This spec is in good shape.*

### MAJOR ISSUES

**M1. KCC-0020 ALIGNMENT CLAIMS ADOPTION OF NON-EXISTENT FEATURES — Lines 330-346**
"Extended state: opaque extended_digest commitment via blake2b" — KCC-0020 calls this `extended_state_digest`, not `extended_digest`. Same field-name mismatch as KCC-0009. Minor but precise terminology matters.

More importantly: KCC-0010 claims "adopts the following from KCC-0020" and lists transfer interface, positional pairing, witness semantics, Borrowed Receive. But KCC-0010's state layout (146-byte KCC-0008 header) is NOT KCC-0020's state layout (owner_identifier + identifier_type + amount + extended_state_digest). KCC-0020's transfer entrypoint operates on `owner_identifier` and `identifier_type`; KCC-0010's operates on `owner_id` and `token_kind`. These are semantically similar but structurally different fields. The "adoption" claim is true at the **pattern** level but not at the **field** level. This distinction should be explicit.

**M2. STATE LAYOUT IS KCC-0008 NOT KCC-0020 — Lines 30-39**
The standard header shown is KCC-0008's (token_id, token_kind, flags, owner_id, amount, metadata_uri, extended_digest). KCC-0020 has: owner_identifier, identifier_type, amount, extended_state_digest. KCC-0010 correctly credits KCC-0008 in lines 341-346, but the main KCC-0020 Alignment section (330) doesn't acknowledge that the base state layout comes from KCC-0008, not KCC-0020. The relationship is: KCC-0010 extends KCC-0008 which itself extends KCC-0020. Three-level chain must be documented.

**M3. MISSING ✓/✗ FEATURE TABLE — Line 330 (KCC-0020 Alignment)**
KCC-0010 DOES have `transfer(State[], Sig[], byte[])` so the mandatory ✓/✗ table for non-transfer specs doesn't apply. However, KCC-0008-quality-template recommends this for all specs with extensions. KCC-0010 adds fee deduction + multi-UTXO output on top of KCC-0008's transfer — a ✓/✗ table showing what KCC-0008 does vs. what KCC-0010 adds would be valuable. This is a quality recommendation, not a blocker.

**M4. DESCRIPTOR MISMATCH WITH KCC-0020 — Lines 234-241**
KCC-0010's descriptor has `token_ids: uint64[]` and `fee_schedule: FeeScheduleEntry[]`. KCC-0020's descriptor has `extended_state_layout: ExtendedStateLayout | none` and `kcc20_extensions: ExtensionId[]`. KCC-0010 adds two fields KCC-0020 doesn't have and drops `extended_state_layout`. The field `kcc20_extensions` is preserved. The KCC-0020 Alignment section says "Descriptor: prefix/suffix covenant script bytes for template identification" — true but incomplete; the descriptor's contents differ substantially.

**M5. BURN AUTH MODEL INCONSISTENCY — Lines 201-215**
`burn(token_id, amount)` says "Caller must be the holder." But `freeze` says "Caller must be the covenant owner" and `mint` says "Caller must be the covenant owner." So burn is holder-authorized but freeze/mint are owner-authorized. KCC-0008's `burn` is also holder-authorized (line 135), so this is consistent with KCC-0008, BUT: in a fee-on-transfer context, if the holder burns their tokens, no fee is paid (rule 16). This means burn can be used to avoid fees — holder transfers to themselves, then burns. Intentional? Not documented.

**M6. FREEZE SCOPE AMBIGUITY — Lines 216-227**
`freeze()` "Sets/clears BIT_FROZEN on the covenant-level state." But KCC-0010's state layout has per-UTXO states. Does freeze apply to all UTXOs for all token_ids in the deployment? Or per-token_id? The state layout shows the fee schedule is global (line 146), so naturally freeze would be global too — but this isn't stated. Also line 227: "mint and burn may still be permitted while frozen (implementation-defined)" — a standard that says "implementation-defined" for a behavioral question is incomplete. Sutton will want a definitive answer.

### MINOR ISSUES

**m1. Line 41**: "KCC-0010 restricts token_kind to FUNGIBLE (0x00)" — but the header at line 34 shows `token_kind` with `// 0x00 = FUNGIBLE`. What happens if someone deploys with token_kind = 0x01? Should mint reject, or is this a deployment-time check? Not specified.

**m2. Line 82**: "Each bps must be ≥ 1 (a zero-bps entry is meaningless; omit it instead)" — but bps could be 0 for an entry that exists for future configurability (if schedule weren't locked). Nit.

**m3. Line 124**: `MIN_OUTPUT = 1` — this is fine for uint64 amounts, but what about tokens with high decimals where 1 unit is microscopic? A MIN_OUTPUT default of 1 is reasonable but should be acknowledged as a parameter the implementer may adjust.

**m4. Line 314 (fee routing example)**: `Output UTXOs: [0] amount=930000 owner=recipient [1] amount=20000 owner=PLATFORM [2] amount=50000 owner=CREATOR` — "PLATFORM" and "CREATOR" are human-readable names, not bytes32 identifiers. In a spec, they should be hash values. Nit.

**m5. Line 386**: Lack of `Updated` field in metadata table (has Created only). Compare with KCC-0009 which has both.

**m6. Line 403-405**: References KCC-0008, KCC-0020, KCC-0021 — all unpublished. Same dependency chain issue as KCC-0009.

## KCC-0011: CONDITIONAL TOKEN

### BLOCKERS

**B1. MATH ERROR IN RESOLVE PRICE COMPARISON — Line 243**
``` 
threshold_scaled = condition_params.threshold * (10 ^ condition_params.threshold_decimals)
```
Per lines 102-108, `threshold = 10` with `threshold_decimals = 2` represents `0.10`. So `threshold_scaled = 10 * 10^2 = 1000`. But this variable is NEVER USED — line 245 uses `condition_params.threshold * attestation.price_denominator` directly. The computation on line 243 is dead code AND the variable name `threshold_scaled` is misleading (it's the threshold in atomic units, not "scaled"). Remove it or use it.

More critically, line 244-245:
```
attested_price_scaled = attestation.price_numerator * (10 ^ condition_params.threshold_decimals)
Condition is MET if attested_price_scaled > condition_params.threshold * attestation.price_denominator
```

The comparison `price_numerator * 10^decimals > threshold * price_denominator` is algebraically equivalent to `price_numerator / price_denominator > threshold / 10^decimals` — this is CORRECT. But `attested_price_scaled` on line 244 is computed and used on line 245 — so line 243's `threshold_scaled` is truly dead. This is a spec artifact, not a math error, but Sutton reads every line.

**B2. ATTESTATION CONDITION_HASH IS UNDEFINED — Line 258**
"Compute `attested_hash` from the attestation payload (or a designated extension field)" — WHERE in the KCC-0017 attestation payload? KCC-0017 defines a 161-byte blob with: version, pair, price_numerator, price_denominator, timestamp, block_height, nonce, operator_id, signature. There is no `condition_hash` field in KCC-0017. So either (a) the ATTESTATION type uses a different attestation format than KCC-0017, or (b) there's an extension field in KCC-0017 that carries arbitrary attested data. Neither is specified. This makes the ATTESTATION condition type unimplementable from this spec alone. **This is a blocker.**

**B3. MISSING ✓/✗ FEATURE TABLE — Line 335 (KCC-0020 Alignment)**
KCC-0011 has `transfer(State[], Sig[], byte[])`, so the strict non-transfer-spec rule doesn't require a ✓/✗ table. BUT: KCC-0011 adds `resolve`, `check_and_transfer`, and `revert` — entrypoints with NO KCC-0020 analogue. The KCC-0020 Alignment lists prose extensions but no table. For a spec this complex (6+ entrypoints, 4 condition types, oracle integration), a ✓/✗ table is essential for reviewability. KCC-0008-quality-template recommends this for all extension specs.

**B4. MISSING FORMULA SECTION FOR CONDITION EVALUATION — Lines 241-261**
The resolve entrypoint has 8 verification steps with inline pseudo-code. Per KCC-0008-quality-template: "include a dedicated section with precise mathematical formulas — not prose descriptions." The condition evaluation logic is described in prose inside the resolve entrypoint rules. It should be extracted to a `## Condition Evaluation Formulas` section with:
```
MET(H, condition_type, params, attestation) = ...
```
per condition type, with exact formulas.

### MAJOR ISSUES

**M1. max_attestation_age NOT IN STATE LAYOUT — Line 233, 316**
`max_attestation_age` appears in the descriptor (line 316: `max_attestation_age: uint64`) and is referenced in resolve rule 5 (line 233). But it's NOT in the covenant state layout. Where does it live? If it's a deployment constant embedded in the covenant script (not mutable state), that should be explicit. The descriptor implies it's per-deployment but mutable state implies it can change. If it's a script constant, it should be documented as such and the descriptor should cite it as derived from the covenant template, not stored in mutable state.

**M2. ORACLE REGISTRY ID NOT IN STATE — Lines 238, 317**
`oracle_registry_id` appears in the descriptor (line 317: `oracle_registry_id: bytes32`) and resolve rule 7 (line 238: "The registry covenant ID is a deployment parameter"). Same issue as M1 — deployment parameter but not in state. What format? Covenant ID? Bytes32 hash?

**M3. NONCE STORAGE FOR REPLAY PROTECTION — Line 236**
"If a prior attestation was consumed by this covenant for this token_id, verify nonce > previous_nonce" — where is `previous_nonce` stored? It's not in the conditional token extended state (106 bytes, fully accounted for). Is there a companion state? KCC-0008 has an allowance companion covenant (lines 160-169). Does KCC-0011 need a nonce companion? Not specified.

**M4. CHECK_AND_TRANSFER SIGNATURE MODEL — Lines 280-285**
`check_and_transfer(attestation_blob, next_states, signatures, witnesses)` combines resolve + transfer. But resolve is permissionless (anyone can call) while transfer requires owner authorization. If `check_and_transfer` is called by a non-owner: (a) resolve succeeds, status → MET, (b) transfer fails because signatures[0] doesn't validate for the owner. Then the status is MET but the transfer didn't happen — is this state valid? The spec says "If status is FAILED, the entire call reverts" (line 292), but what about status=SUCCESS with failed transfer? This edge case is undocumented.

**M5. KCC-0020 FIELD NAME ERROR — Line 343**
"Extended state: opaque extended_digest commitment via blake2b over the conditional token extended state" — KCC-0020 calls it `extended_state_digest`, not `extended_digest`. Same error as KCC-0009 and KCC-0010. All three specs share this mistake.

**M6. TRANSFER STATUS GATING OVERLAP WITH KCC-0008 — Lines 201-203**
"Rules enforced (in addition to all KCC-0008 transfer rules): 1. For each consumed state: status must be MET." But KCC-0008 rule 5 says "BIT_FROZEN must not be set." If BIT_FROZEN is set but status is MET — transfer blocked by KCC-0008? If status is MET but BIT_FROZEN is set — transfer blocked? The interaction between KCC-0008's freeze and KCC-0011's status gate should be explicit.

**M7. REVERT PRESERVES STATUS — Lines 270-275**
"On revert, a new UTXO is produced with owner_id = revert_recipient, preserving... all conditional extended state fields. The new state retains status for auditability." So after revert, the token is held by revert_recipient with status=FAILED or EXPIRED. Can this UTXO be transferred? Rule 7 says "transfer fails if status ≠ MET." So reverted tokens are permanently locked. Is this intentional? A sentence clarifying "After revert, the token becomes permanently non-transferable (terminal audit state)" would help.

### MINOR ISSUES

**m1. Line 18**: "This standard builds on KCC-0008... KCC-0017... KCC-0018" — all unpublished. Dependency chain not acknowledged.

**m2. Line 63**: `oracle_operator_id: bytes32 (SECP256k1 compressed pubkey, 32 bytes)` — SECP256k1 compressed pubkeys are 33 bytes (prefix byte + 32 bytes of x-coordinate). A 32-byte value could be the x-coordinate only, or a pubkey hash. Needs clarification.

**m3. Line 113**: `BLOCK_REACHED (0x02)`: "The condition evaluates as `attestation.block_height >= block`" — but `block` is in `condition_params`, while `deadline` in the extended state (line 64) is also a block height. What's the relationship? If deadline is a block height and BLOCK_REACHED also specifies a block height, can BLOCK_REACHED's block exceed deadline? The spec should say: `BLOCK_REACHED.block <= deadline` or the token expires before the block is reachable.

**m4. Lines 176-182**: `mint_batch(ConditionalMintParams[])` — `ConditionalMintParams` is described inline as a struct. In SilverScript, how is this struct encoded in the transaction input data? Unlike KCC-0008's `mint_batch` which uses `MintParams[]` (described similarly), there's no ABI definition. This is minor but if KCC-0016 (Covenant ABI) is cross-referenced, the encoding should be consistent.

**m5. Line 152**: `If token_kind == NON_FUNGIBLE (0x01): amount must equal 1` — this says "must equal" but then line 153 doesn't enforce it for `FUNGIBLE`. Consistent with KCC-0008.

**m6. Line 316**: Descriptor has `condition_types: uint8[]` "per token_id, in same order" as `token_ids: uint64[]`. This presupposes both arrays have the same length. Should be explicit: `condition_types.length == token_ids.length`.

**m7. Line 397**: Reference lists KCC-0001, KCC-0008, KCC-0017, KCC-0018, KCC-0020, KCC-0021 — six unpublished standards. By far the deepest dependency chain.

## CROSS-CUTTING ISSUES (ALL THREE SPECS)

### CRITICAL: Extended_digest vs extended_state_digest
All three specs reference `extended_digest` in their KCC-0020 Alignment sections, but KCC-0020 calls this field `extended_state_digest`. This is a systematic error. Sutton co-authored KCC-0020 — he will notice.

### CRITICAL: Unpublished dependency chains
KCC-0009 depends on: KCC-0001, KCC-0008, KCC-0020, KCC-0021
KCC-0010 depends on: KCC-0008, KCC-0020, KCC-0021
KCC-0011 depends on: KCC-0001, KCC-0008, KCC-0017, KCC-0018, KCC-0020, KCC-0021

None are merged to main. While this is a publishing-order concern, the reference sections should acknowledge the dependency DAG. If KCC-0011 cites KCC-0017 for attestation format and KCC-0017 hasn't been accepted, the reference is to an evolving draft.

### MAJOR: All three specs conflate KCC-0008 with KCC-0020
KCC-0020 is an interface-level spec (no byte offsets). KCC-0008 is a byte-level spec (146-byte header with offset tables). All three KCCs use KCC-0008's state layout and KCC-0008's field names (owner_id not owner_identifier, token_kind not identifier_type, extended_digest not extended_state_digest). Their KCC-0020 Alignment sections claim to "adopt" from KCC-0020 but actually adopt from KCC-0008. The relationship is: KCC-0020 defines the pattern, KCC-0008 concretizes it at byte level, KCC-0009/10/11 extend KCC-0008. This three-layer architecture must be unambiguous.

### MAJOR: No spec defines `State` struct encoding
All three specs' `transfer(State[] next_states, Sig[] signatures, byte[] witnesses)` signatures reference `State` as a parameter type. KCC-0020 defines `State` as the state fields. KCC-0008 defines byte offsets. But none of them specify how `State` is serialized when passed as an entrypoint parameter. Is it the raw bytes? An ABI-encoded struct? This is the gap between "state layout" (on-chain UTXO data) and "entrypoint parameter" (sigscript input data). KCC-0016 (Covenant ABI) might address this, but it's also unpublished.
